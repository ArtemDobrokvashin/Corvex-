# Эксперимент: защитный mailet James

**Не включать и не использовать для реальной почты.** Код не подключён к
Compose, не входит в образ и не является готовым AV-конвейером. Это кандидат
под API Apache James 3.9.1: он наследует `ClamAVScan` для штатного подключения к
clamd, но не использует его fail-open `service` и разбор ответа. Сканирует
сообщение заново, не доверяя пользовательским заголовкам и старым атрибутам;
только точный `stream: OK\0` оставляет исходный state. MIME сериализуется
непосредственно в ограниченный по числу байт INSTREAM, без использования
`MimeMessageInputStream` с его потенциальной полной материализацией в памяти. Инфицированный и
неизвестный результаты отправляются в отдельные состояния, которые **пока не
сконфигурированы**. При отсутствии процессоров нельзя включать mailet.

Не проверены classloading в образе, привязка к живому ClamAV, отображение ошибок, безопасность state transitions и
персистентность quarantine/recovery. Кандидат ограничивает общее время TCP connect тремя секундами и числом
адресов. Для обмена сокет закрывается watchdog по общему сроку 30 секунд;
при этом зависшее чтение MIME-входа и DNS в унаследованной инициализации
могут не прерваться. Планировщик и реальные ОС/James не испытаны под нагрузкой,
поэтому общий срок не является доказанной гарантией для всего сообщения.
Инициализация не использует fail-open `ClamAVScan.init()`: host обязателен,
порт проверяется, неподдержанные параметры отвергаются; TCP-подключение при
старте не проверяется. DNS разрешается один раз при старте и может зависнуть;
после смены адреса ClamAV автоматического обновления нет. Кандидат не включён,
инициализация проверена с настоящими зависимостями в unit-тесте, но в контейнере не проверена.
Лимит
сообщения и настройки ClamAV должны согласовываться с SMTP; пути JMAP import,
APPEND и internal могут обходить mailet. Согласно исходникам James 3.9.1,
[`Email/import`](https://github.com/apache/james-project/blob/james-project-3.9.1/server/protocols/jmap-rfc-8621/src/main/scala/org/apache/james/jmap/method/EmailImportMethod.scala) вызывает `mailbox.appendMessageReactive` напрямую, минуя spool;
[`EmailSubmission/set`](https://github.com/apache/james-project/blob/james-project-3.9.1/server/protocols/jmap-rfc-8621/src/main/scala/org/apache/james/jmap/method/EmailSubmissionSetMethod.scala) ставит письмо в spool. Это анализ исходников, не live test.

Прежний `jmap-nginx.conf` ограничивает HTTP-пути, но **не** JMAP-методы в
JSON: обладатель bearer token и сетевого доступа к POST /jmap может попытаться
выполнить запись. Подготовленный read-only шлюз проверен на ноутбуке с реальным
James и теперь указан в Compose-профиле, но уже работающий nginx не меняется без
пересоздания. Шлюз не закрывает прямой доступ к James по другим сетям и не
обеспечивает AV/owner/RBAC. До включения пользовательских путей необходимо
проверить все записи; mailet сам по себе не защищает JMAP import.
Не использовать этот класс, пока они не закрыты и пока реальные письма и
вложения не проходят проверку. EICAR/недоступность/сбои/restart/rollback не
проверены в James. `ToRepository` без потерь и без bounce пока лишь направление.

Локальная синтетическая проверка JDT 17 с временными заглушками James/JavaMail:
успешная компиляция, точный CLEAN, FOUND, ошибки/обрыв/пустой ответ и null MIME
переводятся в ожидаемые состояния. Это не компиляция против реальных James jar,
не Maven и не живая проверка. `scripts/tests/test_james_av_candidate.py` — лишь
структурные проверки; они не подтверждают работоспособность или защиту.

Повторяемая синтетическая проверка с JDK 17: `sh experiments/james-av-gate/test-stubs.sh`.
Она собирает кандидат против **искусственных заглушек**, запускает локальный
fake scanner и проверяет маршрутизацию результатов и зависания read/write на
сокете. Заглушки не включаются в образ; проверка не заменяет Maven с настоящими
зависимостями James или ClamAV и не доказывает безопасность всего конвейера.

Отдельный `pom.xml` подготовлен для будущей компиляции и unit-тестов с настоящими
артефактами James 3.9.1: `mvn -f experiments/james-av-gate/pom.xml test`.
**Для Maven нужен JDK 21 или новее**: исходники James 3.9.1 настроены на Java 21,
его опубликованные классы имеют версию 65. Попытка на ПК с Java 17 для исходного
POM завершилась `BUILD FAILURE` из-за несовместимой версии классов. Артефакты
были загружены, но компиляция и тесты против них не прошли; POM исправлен на 21,
повтор с JDK 21 для версии `d8e27cc` на ПК: 2 теста, 0 ошибок,
BUILD SUCCESS. Позднее версия `7df6221` на ПК: Maven с реальными зависимостями James,
5 unit-тестов, 0 ошибок/пропусков, BUILD SUCCESS. Они используют fake Mail и
fake clamd, не запущенный James или реальный сканер. Скрипт `test-real-dependencies.ps1`
подготовлен для пакетной проверки на Windows с JDK 21+ и fake clamd. Синтетический stub runner по-прежнему можно
запускать с JDK 17 — он не использует настоящие зависимости. Даже успешная Maven-сборка не
проверит загрузку класса внутри образа James, реальные clamd, карантин или ingress.

Важные ограничения, обнаруженные по исходникам 3.9.1: если состояние доходит до
конца processor без смены, `MailetProcessorImpl` может перевести письмо в GHOST;
пустой quarantine processor не является удержанием. У default error processor
есть Bounce. Postgres repository сначала сохраняет MIME blob, затем метаданные
с upsert по URL/ключу; атомарность между blob/БД и поведение при падении не
доказаны. Поэтому для INFECTED/UNKNOWN требуются реальная конфигурация
удержания, проверка обработки ошибок и recovery, без bounce с вложением.
[MailetProcessorImpl](https://github.com/apache/james-project/blob/james-project-3.9.1/server/mailet/mailetcontainer-impl/src/main/java/org/apache/james/mailetcontainer/impl/MailetProcessorImpl.java),
[PostgresMailRepositoryContentDAO](https://github.com/apache/james-project/blob/james-project-3.9.1/server/data/data-postgres/src/main/java/org/apache/james/mailrepository/postgres/PostgresMailRepositoryContentDAO.java).
Лимит собственного INSTREAM не гарантирует ограничения памяти внутри самой
реализации MIME, таймаута источника, настроек clamd или размера входа SMTP.

### Неполное сканирование ClamAV

По [примеру конфигурации ClamAV 1.5.4](https://github.com/Cisco-Talos/clamav/blob/clamav-1.5.4/etc/clamd.conf.sample)
`ScanMail` по умолчанию включён, однако `AlertExceedsMax` по умолчанию выключен.
Без этого предупреждения превышение `MaxFileSize`, `MaxScanSize` или
`MaxRecursion` может оставить вложенный контент непроверенным; `OK` одного
протокольного ответа не доказывает, что всё содержимое действительно проверено.
Нужно отдельно подтвердить фактическую конфигурацию образа, согласовать лимиты,
включить и проверить сообщения об исчерпании лимитов, а также исследовать
`MaxFiles`, `MaxScanTime` и другие случаи неполного сканирования. Кандидат
маршрутизирует ответ с сигнатурой `Heuristics.Limits.Exceeded... FOUND` как
UNKNOWN, а не как доказанный вирус. Синтетическая проверка этого поведения не
подтверждает настройки или поведение настоящего clamd. Ничего в существующем
контейнере или его конфигурации не менялось.

### Подготовка перехода к проверке в существующем James

`mailetcontainer.candidate.xml` — **отключённый пример**, основанный на
[конфигурации PostgreSQL James 3.9.1](https://github.com/apache/james-project/blob/james-project-3.9.1/server/apps/postgres-app/sample-configuration/mailetcontainer.xml).
Он помещает gate первым в spool `root`, направляет INFECTED и UNKNOWN в разные
Postgres-репозитории и убирает Bounce из общего processor `error`. Проверки
`scripts/tests/test_james_av_pipeline_candidate.py` проверяют только структуру
XML. Это не утверждение, что spool/repository/retry устойчивы или что AV покрывает
все входы: `Email/import`, IMAP APPEND и другие прямые записи обходят spool.
Значение `clamav` в примере пока **недоступно** из изолированной сети James:
текущий clamd находится в сети `app`. Настройки сетей или Compose не менялись.

[Образ James 3.9.1](https://github.com/apache/james-project/blob/james-project-3.9.1/server/apps/postgres-app/pom.xml)
предусматривает `/root/extensions-jars` для внешних jar; в
[README образа](https://github.com/apache/james-project/blob/james-project-3.9.1/server/apps/postgres-app/src/main/extensions-jars/README.md)
этот каталог описан как classpath для custom mailets. Наш класс наследует
`ClamAVScan`: кроме собранного jar ему нужен `apache-james-clamav` 3.9.1 в
classpath, если этот класс отсутствует в самом образе. `provided` в нашем POM
не включает эту зависимость в jar. Текущий образ на ПК, точный classloader,
совместимость зависимостей и загрузка **не проверены**. Не подменять entrypoint
и не копировать случайные версии библиотек: сначала определить фактический
classpath и сделать однократную проверку на синтетических данных в существующем
James с подготовленным откатом.

Прежде чем вообще предлагать временное включение, нужен объединённый сценарий:
проверить наличие кода в classpath и его инициализацию; конфигурацию и сетевой
доступ к clamd; реальный CLEAN/EICAR и ошибку/лимиты/недоступность; отдельно
убедиться, что письма удерживаются в нужных репозиториях без bounce, а при
ошибке БД/рестарте не теряются; вернуть исходные настройки. Исключение из
`ToRepository` передаётся дальше в коде `ProcessorImpl`, но итог очереди и
восстановление в текущем образе остаются неизвестными. Этот кандидат нельзя
применять к пользовательским сообщениям или использовать как допуск к cutover.

Для последующего опыта Maven `package` дополнительно готовит отдельную копию
`apache-james-clamav-3.9.1.jar` в `target/extension-deps/`; сам проектный jar
остаётся в `target/`. Это не fat jar и автоматически в James не устанавливается.
Новая стадия packaging ещё не запускалась с настоящим Maven, а копию upstream jar
следует использовать только после проверки отсутствия конфликтующей версии в
образе. Старые результаты `mvn test` этого packaging не проверяют.

`test-real-dependencies.ps1` теперь выполняет Maven `package` и проверяет наличие
обоих файлов jar. `test-container-classpath.ps1 -ConfirmLaptop`, запущенный из
каталога рабочего Compose **после упаковки**, выполняет отдельную краткую JVM
в уже запущенном контейнере James без перезапуска и без обработки писем. Он
выясняет, есть ли класс `ClamAVScan` в стандартном Jib classpath, при отсутствии
использует отдельный upstream jar только в этой JVM, затем пытается создать
кандидата через Mailet API. Временные файлы помещаются в уникальный `/tmp` и
удаляются. Эти два обновлённых сценария на Windows/Docker пока не запускались;
в реальном James classloader, конфигурацию, clamd и обработку почты они не
проверяют и в сервис ничего не устанавливают.

### Кандидат подключения к существующему Compose

`infra/james/candidates/av-runtime.compose.yml` — **не активируется автоматически**.
Он предназначен для будущего включения в существующем проекте Corvex: добавляет
только James и ClamAV в отдельную внутреннюю сеть, монтирует два собранных jar и
candidate XML в James read-only. Путь исходных файлов рассчитан относительно
корневого `docker-compose.yml`, который должен быть первым Compose-файлом.
Файлы jar должны существовать до создания контейнера; `create_host_path: false`
предотвращает автоматическое создание каталогов вместо отсутствующих файлов.
Подключение overlay может пересоздать **существующие** James и ClamAV и временно
остановить их: это не отдельный стенд. Обычная конфигурация и пользовательские
почтовые маршруты этим файлом сами по себе не меняются.

Этот файл — только подготовка состава контейнера. Проверка загрузки gate в
живом процессе James, сетевого доступа и эффектов compose merge ещё не
выполнена. Два сервиса получают взаимную сетевую достижимость; доступ ко всем
слушающим портам на этой сети не ограничен только clamd. Не включать overlay
для пользовательского потока: маилет не покрывает прямой JMAP import и IMAP
APPEND, настройки ClamAV и устойчивость карантина неизвестны. Перед живым
экспериментом необходим сценарий восстановления прежних конфигурации и сетей,
проверка незавершённых писем и реальные CLEAN/EICAR/недоступность сканера.

### Ограничение адреса сканера

Кандидат разрешает `host` при инициализации и сохраняет полученные адреса.
После пересоздания ClamAV его адрес в Docker-сети может измениться: до
перезапуска/переинициализации mailet проверки могут оставаться UNKNOWN даже
после восстановления ClamAV. Это fail-closed отказ доступности, а не recovery.
Автоматическое обновление DNS и его ограничение по времени пока не реализованы;
включать candidate в рабочий путь до проверки этого сценария нельзя.
