# James JWT/HTTPS: изолированный синтетический тест

Не подключать к рабочему Corvex, реальным пользователям, данным или ключам.
Проект создаётся с новым случайным именем Compose и отдельными томами. WebAdmin
отключён, James и PostgreSQL изолированы; наружу доступен только TLS-прокси на
`127.0.0.1:18443`. Прокси также подключён к отдельной обычной bridge-сети
для публикации порта; только он может иметь сетевой выход через эту сеть. Прокси — учебный, не production: TLS завершается на нём, а
дальше до James используется HTTP внутри отдельной сети. Публичные пароли
учётных записей `user01/02@james.local` — `1234`.

На ПК с Java 17/JDK, keytool, Maven, Docker и Compose из корня лабораторной
копии: `powershell -ExecutionPolicy Bypass -File experiments/james-jwt-lab/run-lab.ps1`.
Скрипт создаёт уникальную папку в `%TEMP%` с новой парой RSA для JWT и TLS
сертификатом для localhost и передаёт тестовое хранилище сертификатов только
в forked JVM тестов через профиль Surefire; Maven использует обычное системное
хранилище для скачивания зависимостей. Затем скрипт запускает отдельные контейнеры, создаёт демо-пользователей и выполняет
все James JUnit тесты, включая live. Он проверяет свежий отчёт live-теста и
отклоняет skipped/failed; в `finally` останавливает только созданный проект,
но не удаляет его тома, контейнеры или тестовые ключи. Имена и расположение
печатаются в выводе. Не использовать `down -v`, prune или очистку рабочих томов.

Результат не подтверждает production TLS, настоящий сервис Corvex, RBAC,
2FA, отзыв, AV/spam, SMTP, миграцию или backup. До live прогона работоспособность
конфигурации и совместимость с James 3.9.1 остаются гипотезой. Не смешивать
эту экспериментальную конфигурацию с основным docker-compose.yml.

В новой версии перед Java-тестами отдельный кратковременный контейнер `seed`
добавляет **одно синтетическое письмо с вложением** в user01 через IMAP. Live
Java-тест должен найти его через JMAP и не допустить user02 к идентификатору
чужой папки. Эта новая версия ещё не проверена на ПК: unit/mock и live сценарии
могут обнаружить проблемы. Она не проверяет байты вложения через Java клиент.

Дополнительно live-набор исследует account-level `Email/get.state`: фиксирует
статус, через контейнер `seed` помечает одно синтетическое письмо прочитанным,
затем добавляет ещё одно, после каждого действия ждёт изменения state. Контейнер
`seed` используется только с уникальным project `corvex-jwt-lab-<hex>` и этим
файлом Compose; другие режимы, кроме `append` и `seen`, отвергаются. Это лишь
проверка конкретных случаев, не доказательство атомарной пагинации: индексация,
перемещение, удаление, конкурентные операции и задержки событий требуют тестов.
Эта расширенная версия ещё не запускалась на ПК.

После Java-тестов общий runner дополнительно запускает синтетический IMAP
round-trip: две отдельные копии одинакового MIME-письма с вложением и разными
флагами Seen; проверяет идентичность всех байтов и флаги каждой копии. Это
первый кандидат live-проверки: до запуска на ПК он не проверен с James. Он не
переносит почту Corvex и не проверяет production TLS, AV, доставку, рестарт,
папки или согласованность снимка. Следы остаются только в новых тестовых томах.

ПК: прежний round-trip двух копий без перезапуска прошёл (b12c459). Следующее
расширение добавляет обычный `restart` только синтетического James и повторное
чтение тех же копий в readonly IMAP-сессии. Это новый, ещё не выполненный live
сценарий; обычный рестарт не равен crash/power-loss или backup/restore проверке.

Следующее расширение связывает синтетический файл-снимок и IMAP чтение после
рестарта: вычисляет исходный манифест и сверяет реальные байты и флаги двух
копий с ответом James. Сопоставление копий в тесте задано искусственно по
флагу Seen и применимо **только к этим фикстурам** — это не алгоритм реального
переноса и не доказательство достоверности production-сопоставления. Live
прогон новой версии ещё не выполнен.

Следующее расширение общего прогона создаёт отдельную **синтетическую** базу
`corvex_fixture` в PostgreSQL нового лабораторного проекта, применяет V1 схему
mail-storage, вставляет одну фикстуру и запускает read-only экспорт. Дальше
отдельный контейнер сопоставляет метаданные с синтетическим файлом и строит
манифест. К существующим БД Corvex он не подключается. Сценарий ещё не прошёл
live-проверку; он не подтверждает согласованность реальных файлов и БД или
перенос в James. Выгрузка и база останутся среди тестовых данных проекта.

Дополнительный кандидат live-теста использует только тестовый `user01` и
краткоживущий JWT для загрузки multipart MIME в JMAP, `Email/import`, скачивания
полного blob и сравнения байтов и флагов. Он выполняется внутри изолированной
Docker-сети напрямую по HTTP к тестовому James; это не production TLS и не
production-клиент. Тест не делает повтор при ошибке импорта. Токен лежит в
`export` тестового каталога и истекает через три минуты. Новый тест пока не
запускался против James: расхождение байтов или ошибка протокола будет FAIL и
потребует анализа; совпадение одного примера не доказывает безопасность импорта
всех MIME-писем, повторов, идентификации или доставки.

ПК: JMAP upload/import/download вернул другие байты для synthetic multipart
(a2e3889): source SHA-256
`df7e3666b71cf7b5020d370168fc7c4f4f5044900a0e77623f21e86d2d0b6267`,
returned SHA-256
`9a6a8bf0179d5be296eeaf7ad16bf71d92720b7a1b1bab9562f362f385caff0e`.
Флаги после JMAP не проверены, поскольку тест остановился на сравнении байтов.
Причина и точный этап изменения не установлены. Путь запрещён для точного
переноса до выяснения; не делать retry автоматически. Из обычного прогона этот
известно неуспешный диагностический тест убран с явным предупреждением; при
явном `JAMES_LAB_RUN_JMAP_IMPORT_DIAGNOSTIC=1` он по-прежнему выполнится и
ошибка байтов останется ошибкой.

Успешный результат не докажет безопасные повторы, другие письма или delivery.

Подготовлен новый синтетический вертикальный сценарий: сохранение фиксированного

Этот код предназначен только для данного теста, не для реальной миграции:
новая версия использует APPENDUID и сравнивает UIDVALIDITY до и после APPEND;
эти проверки пока выполнялись только на mock и не проверены live; не
проверены восстановление с James, полномочия,
большие файлы, стабильный snapshot или прочность записи на конкретном диске.
Потеря ответа переводится в uncertain и автоматически не повторяется.
