# Надёжное хранение почты: исследование и проект для проверки

**Статус: проект, не реализация и не разрешение на развёртывание.** На рабочем
стенде до отдельной приёмки не использовать перенос, архивирование или удаление
писем. Промежуточная версия в рабочей ветке сохраняет исходные файлы после
MOVE/RENAME и тела после протокольного удаления. Это только эксперимент:
неограниченное хранение занимает место и сохраняет конфиденциальные данные.
На рабочий сервис изменения не установлены. Не запускать очистку найденных копий.

## Подтверждённые наблюдения

* В изолированном тесте с PostgreSQL и реальными webmail-методами изменение
  флагов, начатое до MOVE, вернуло в БД устаревшую папку и путь. Блокировка
  строки устранила проверенный сценарий; варианты webmail и протокольного API
  изменения флагов против webmail MOVE прошли. Это не доказывает причину
  исторического инцидента и не покрывает все пути обновления.
* На синтетических данных подтверждены: потеря файла при откате EXPUNGE/POP3,
  потеря при откате удаления и переименования папки, удаление общего файла при
  MOVE или удалении одной из двух записей. Промежуточные варианты закрыли
  проверенные последовательности, сохраняя старые копии.
* Детерминированный тест воспроизвёл TOCTOU: после подсчёта одной ссылки другая
  транзакция создала новую ссылку, а очистка всё равно удалила файл. Из этого не
  следует, что именно такая ссылка создавалась в реальном инциденте.
* На ПК прошли полный Maven и 11 тестов для предыдущего кандидата; затем при
  проверке гонки 11 из 12 прошли, один показал проблему. Последняя команда с
  временным отказом от физической очистки завершилась `BUILD SUCCESS`, но сводка
  последнего изолированного набора и факт выполнения обеих стадий ещё не получены.

## Что говорит документация

1. При PostgreSQL Read Committed снимок обычного SELECT относится к началу
   конкретного запроса; повторный запрос может увидеть другие данные. Блокировка
   одной строки не запрещает вставить другую строку, ссылающуюся на тот же путь.
   Для инварианта нужны общий объект блокировки и дисциплина **всех** писателей;
   advisory lock сам по себе не принуждает неучаствующий код к соблюдению правил
   ([PostgreSQL 16: изоляция](https://www.postgresql.org/docs/16/transaction-iso.html),
   [1](https://www.postgresql.org/docs/current/explicit-locking.html)).
2. `afterCompletion` — callback процесса, а не долговечная очередь. При потере
   процесса он может не исполниться; статус UNKNOWN нельзя трактовать как commit
   или rollback. Для DB-запроса из callback нельзя рассчитывать на новую транзакцию
   без явного управления ресурсами. Это согласуется с
   [документацией Spring TransactionSynchronization](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html).
3. Outbox фиксирует намерение вместе с изменением БД; самостоятельный обработчик
   должен выдерживать повтор и сбои. Сам по себе outbox **не делает** filesystem
   частью транзакции PostgreSQL и не гарантирует exactly-once
   ([AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)).
4. `fsync` файла не гарантирует долговечность записи в каталоге. Для Linux
   необходимо учитывать синхронизацию каталогов и ошибки; rename через разные
   ФС и гарантии Docker Desktop/Windows требуют отдельной проверки
   ([Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)).
5. Dovecot описывает иммутабельность доставленного сообщения и отделяет UID от
   имени файла; его реализация не равна реализации Corvex. Нельзя считать
   совместимость с произвольными Maildir-клиентами доказанной
   ([Dovecot Maildir](https://doc.dovecot.org/2.3/admin_manual/mailbox_formats/maildir/)).

## Предлагаемое направление: иммутабельное тело и логическая папка

Вместо физического перемещения тела при каждом MOVE рассмотреть отдельный
неизменяемый объект сообщения с независимым, неповторно используемым ID и
стабильным путём. Таблица логических писем ссылается на объект; папка, UID,
MODSEQ, флаги и владелец — данные БД. **MOVE и RENAME меняют БД, а не пути
файлов**. COPY создаёт отдельную запись сообщения; совместное использование
объекта допустимо только с защищённым учётом ссылок. Изменение MIME создаёт
новый объект. Изменять видимость чужого письма нельзя; доступ проверяется по
владельцу логической записи, а не по знанию ID или пути файла.

Это предложение требует проверки совместимости с IMAP UID/UIDVALIDITY,
CONDSTORE, внешней синхронизацией, резервным копированием и всеми операциями.
Сейчас некоторые методы физически используют имя папки в пути; нельзя просто
заменить MOVE на UPDATE без аудита остальных путей, тестов и миграции.
Идентификаторы и уникальные пути не должны быть основаны только на имени папки:
нормализация разных имён может дать одинаковый каталог.

### Управление ссылками и очисткой — предварительный протокол

* Запись объекта `ACTIVE` идентифицирует файл; новые ссылки и удаление ссылок
  сериализуются по **строке объекта**. На уровне базы нужны ограничения/FK и,
  где возможно, enforcement через общий DB-интерфейс/триггеры для всех путей,
  а не только добровольное правило в одном Java-методе. Порядок блокировок для
  нескольких объектов и папок фиксированный; дедлоки и timeout обрабатываются
  как неуспешная операция, не как повод удалить файл.
* При удалении последней ссылки тот же DB-коммит записывает объект в состояние
  `GC_PENDING` и долговечное намерение очистки. Новая ссылка на `GC_PENDING`
  запрещена без безопасного согласованного перехода; обычный `COUNT(*)` вне
  общей блокировки недостаточен. Управление вложениями/CAS — отдельный аналогичный
  инвариант, а не автоматическое следствие этой схемы.
* Worker с правами только на нужное хранилище проверяет состояние/отсутствие ссылок
  под той же блокировкой и выполняет идемпотентную очистку. Протокол удержания
  блокировки, метка состояния и порядок unlink/fsync/DB должны быть доказаны на
  межпроцессных тестах. Если процесс погиб после unlink, но до DB-коммита,
  повтор обрабатывает отсутствие файла только при доказанном состоянии операции;
  произвольный пропавший файл нельзя молча считать успешно удалённым. I/O и fsync
  ошибки, расхождения и неизвестные состояния — карантин и алерт, не «успех».
* Новые записи тел требуют своего безопасного протокола: устойчивый журнал
  намерения, уникальные временные имена, проверка целостности, публикация без
  перезаписи, запись/синхронизация файла и каталогов, затем привязка к БД.
  Оставшиеся файлы staging — не автоматически мусор. Символические ссылки,
  подмену путей и пересечения с другими владельцами нужно исключить.
* Сборщик не должен участвовать в запросе открытого письма или блокировать его
  неоправданно долго; семантику открытых файлов, cancellation, дисковых ошибок,
  квот и блокировок на Linux-контейнере и Windows Server необходимо проверить.
  Состояние GC, объём и возраст очереди, ошибки и задержки должны быть видимы
  администратору. Очистка без этих условий остаётся отключённой.

## Backup и сохранение конфиденциальности

Текущий `scripts/backup.ps1` сначала делает отдельные дампы БД, затем архивы
томов при работающих сервисах. Это **не единый согласованный снимок**: при
параллельной физической очистке файл, нужный старому дампу, может исчезнуть до
архива тома. Нужен спроектированный барьер/снимок, охватывающий все writers и
очистку mail и вложений, а также проверка восстановленной копии. Простая пауза
одного сервиса не доказывает, что другие писатели остановлены. Старые копии,
бэкапы, корзина, версии, сроки физического удаления, доступ администраторов,
шифрование, квоты и юридические требования должны иметь явную политику;
без неё не обещать ни немедленное уничтожение, ни бессрочное хранение.

## Обязательные испытания перед релизом

1. Миграция на копии живых данных: все записи/UID/владельцы/права и байты MIME,
   вложения и исторические дубли. Отдельный проверенный backup и обратимый план;
   никаких автоматических изменений пользовательского тома во время диагностики.
2. Реальный PostgreSQL + ФС + реальные web/IMAP/POP3 сервисы: одновременные
   флаги/MOVE/COPY/EXPUNGE/DELE/RENAME, shared paths, owner isolation, дедлоки,
   отказ и повтор, несколько реплик и неизвестный ответ клиенту.
3. Управляемое завершение процесса на каждом шаге записи и очистки, restart и
   recovery, повторная обработка, нехватка места/прав, отказ БД/ФС, повреждение,
   отсутствие файла, неизвестный commit. SIGKILL приложения не эквивалентен
   отключению питания; отдельно проверять согласованность каталога и host/storage.
4. Нагрузочные проверки и monitoring, сверка файлов и метаданных с неизменяемым
   отчётом, полный backup/isolated restore во время нагрузки, целостность MIME и
   вложений. Проверить совместимость Docker Desktop/Windows Server, не принимать
   fsync/rename гарантии Linux как доказанные для всей цепочки хранения.
5. Только после зелёных интеграционных тестов — обновление тестового стенда с
   проверенным резервным планом, затем полноценная приёмка пользователем. Удаление
   экспериментальных копий — отдельное подтверждённое действие после диагностики.
