# Подготовка James внутри существующего Compose Corvex

Статус: **кандидат инфраструктуры, не подключение и не переключение**.
В главном `docker-compose.yml` добавлен выключенный по умолчанию профиль
`james-transition`: сервисы `james`, `james-postgres` и внутренний TLS
прокси `james-jmap`, отдельные постоянные тома. Внешние порты не публикуются, существующие маршруты и тома не изменены,
сервисы webmail, входящей и исходящей почты на James не перенаправлены.
В `mail-storage-service` добавлены выключенные по умолчанию настройки preview и
read-only mount каталога адаптера; при применении нового Compose этот сервис
может быть пересоздан. Проверка на Windows ещё не проведена.

Не включать профиль и не помещать в него реальные письма до реализации и
проверки пунктов ниже. Compose-профиль — не защита от запуска с `--profile`;
обычный `docker compose up` без него новые сервисы не запускает. Отдельные тома
**не являются backup**. Не применять `docker compose down -v` и prune.

## Перед первым включением требуется

* Подготовлен `scripts/prepare-james-laptop.ps1 -ConfirmLaptop`: он генерирует
  отдельный случайный пароль БД, пару JWT ключей, локальный TLS-сертификат с
  именем `james-jmap` и необходимые файлы в `infra/secrets/james` и
  `infra/secrets/james-adapter` (исключены из Git). Скрипт не меняет `.env`,
  не запускает Docker и не перезаписывает существующие файлы; при частичной
  ошибке оставляет данные на месте для разбирательства. Его выполнение на
  Windows, права доступа и восстановление ключей ещё не проверены. В командной
  строке keytool пароль временного keystore виден локальным администраторам.
* Пароль отдельной БД содержится и в `postgres.properties`, и в `compose.env`.
  Для Compose потребуется явно указать и основной `.env`, и этот env-файл;
  изменение пароля без синхронизации с БД сломает доступ. Эти файлы и JWT/TLS
  ключи требуют ограниченных прав, защищённого backup и политики ротации.
  Переменные контейнера доступны через Docker inspect. Не печатать секреты.
* TLS ограничен только связью Corvex → `james-jmap`: используется отдельный
  сертификат, а не изменение JVM truststore. Прокси и James соединены HTTP
  внутри отдельной внутренней сети, а сам James недоступен в app-сети. Прокси
  фильтрует пути, но **не** ограничивает JMAP-методы; bearer даёт полные права
  ящика. Проверка hostname остаётся включённой. Безопасность сети, права файлов,
  токенов и отзыв ещё не подтверждены.
* Скрипт готовит `search.properties` с `implementation=scanning` **только для
  ноутбука**; upstream помечает этот режим непригодным для production. Не
  переносить эту настройку на сервер. `webadmin` выключен, автоматический
  provisioning отключён; полноценное администрирование ящиков ещё не создано.
* Определить поддерживаемую и проверенную поисковую конфигурацию и storage;
  scanning из учебного стенда — не выбор для production. Подтвердить бэкапы и
  восстановление обоих новых томов, размеры и эксплуатационные настройки.
* Реализовать доверенный реестр/provisioning, проверку актуального RBAC и отзыв,
  полное чтение/действия webmail, доставку и исходящие сообщения через James с
  AV/spam, протоколы и app-password. Текущий opt-in preview ограничен первой
  страницей и не является полноценным webmail.
* Перенести копии или согласовать чистое тестовое начало; обеспечить безопасную
  остановку всех писателей, сверку и обратный путь для вновь полученных писем.
  Реальные внешние почтовые аккаунты и их настройки не удалять.

Проектные Compose-изменения проверены только YAML-разбором и статическими
проверками: Docker Compose на Windows, конфигурация, генерация секретов, TLS-прокси,
James startup и этот профиль в реальном Corvex ещё не испытывались. Наличие профиля не подтверждает, что
переход готов. Отдельные синтетические JWT-стенды удалены пользователем без
удаления томов; больше создавать их для этого ноутбука не требуется, если не
понадобится отдельная диагностика по согласованию.
