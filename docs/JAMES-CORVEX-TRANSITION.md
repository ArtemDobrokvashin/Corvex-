# Подготовка James внутри существующего Compose Corvex

Статус: **кандидат инфраструктуры, не подключение и не переключение**.
В главном `docker-compose.yml` добавлен выключенный по умолчанию профиль
`james-transition`: сервисы `james`, `james-postgres` и внутренний TLS
прокси `james-jmap`, отдельные постоянные тома. Внешние порты не публикуются, существующие маршруты и тома не изменены,
сервисы webmail, входящей и исходящей почты на James не перенаправлены.
В `mail-storage-service` добавлены выключенные по умолчанию настройки preview и
read-only mount каталога адаптера. На ноутбуке контейнер пересоздан с этим mount;
проверка транспорта описана ниже.

Не включать профиль и не помещать в него реальные письма до реализации и
проверки пунктов ниже. Compose-профиль — не защита от запуска с `--profile`;
обычный `docker compose up` без него новые сервисы не запускает. Отдельные тома
**не являются backup**. Не применять `docker compose down -v` и prune.

## Перед первым включением требуется

* Подготовлен `scripts/prepare-james-laptop.ps1 -ConfirmLaptop`: он генерирует
  отдельный случайный пароль БД, пару JWT ключей, локальный TLS-сертификат с
  именем `james-jmap` и необходимые файлы в `infra/secrets/james` и
  `infra/secrets/james-adapter` (исключены из Git). Скрипт не меняет `.env`,
  не запускает Docker и не перезаписывает существующие файлы; при частичной
  ошибке оставляет данные на месте для разбирательства. Его выполнение на
  Windows, права доступа и восстановление ключей ещё не проверены. В командной
  строке keytool пароль временного keystore виден локальным администраторам.
* Пароль отдельной БД содержится и в `postgres.properties`, и в `compose.env`.
  Для Compose потребуется явно указать и основной `.env`, и этот env-файл;
  изменение пароля без синхронизации с БД сломает доступ. Эти файлы и JWT/TLS
  ключи требуют ограниченных прав, защищённого backup и политики ротации.
  Переменные контейнера доступны через Docker inspect. Не печатать секреты.
* TLS ограничен только связью Corvex → `james-jmap`: используется отдельный
  сертификат, а не изменение JVM truststore. Прокси и James соединены HTTP
  внутри отдельной внутренней сети, а сам James недоступен в app-сети. Прокси
  фильтрует пути, но **не** ограничивает JMAP-методы; bearer даёт полные права
  ящика. Проверка hostname остаётся включённой. Безопасность сети, права файлов,
  токенов и отзыв ещё не подтверждены.
* Скрипт готовит `search.properties` с `implementation=scanning` **только для
  ноутбука**; upstream помечает этот режим непригодным для production. Не
  переносить эту настройку на сервер. `webadmin` выключен, автоматический
  provisioning отключён; полноценное администрирование ящиков ещё не создано.
* Определить поддерживаемую и проверенную поисковую конфигурацию и storage;
  scanning из учебного стенда — не выбор для production. Подтвердить бэкапы и
  восстановление обоих новых томов, размеры и эксплуатационные настройки.
* Реализовать доверенный реестр/provisioning, проверку актуального RBAC и отзыв,
  полное чтение/действия webmail, доставку и исходящие сообщения через James с
  AV/spam, протоколы и app-password. Текущий opt-in preview ограничен первой
  страницей и не является полноценным webmail.
* Перенести копии или согласовать чистое тестовое начало; обеспечить безопасную
  остановку всех писателей, сверку и обратный путь для вновь полученных писем.
  Реальные внешние почтовые аккаунты и их настройки не удалять.

На ноутбуке проверены Compose-конфигурация, генерация секретов, запуск профиля,
`ListDomains`, синтаксис nginx и транспорт без авторизации (см. ниже). Наличие
профиля не подтверждает, что переход готов. Отдельные синтетические JWT-стенды удалены пользователем без
удаления томов; больше создавать их для этого ноутбука не требуется, если не
понадобится отдельная диагностика по согласованию.

В переходном профиле подготовлены пустые конфигурации native SMTP, IMAP,
POP3, LMTP и ManageSieve James: пока они должны быть выключены, чтобы не
создавать конкурирующие обработчики или демонстрационные TLS-настройки.
Действующие Corvex-протоколы эти файлы не меняют. James запущен с пустыми
конфигурациями на ноутбуке; полноценные протоколы James с настоящей
аутентификацией и TLS предстоит настроить при переключении, нельзя считать их
работающими после старта профиля.

## Проверка внутреннего TLS после запуска на ноутбуке

На проверенном ноутбуке профиль запущен: James и TLS-прокси работают, PostgreSQL
healthy, `ListDomains` и `nginx -t` прошли. Это не проверка почты или TLS-клиента.
Для отдельной проверки пути из уже работающего `mail-storage-service`:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\test-james-transition-tls.ps1
```

Нужен JDK 17 (`javac`) на Windows. Скрипт компилирует временный probe, копирует
его в случайный каталог `/tmp` работающего контейнера, запускает и удаляет. Он
не запускает и не пересоздаёт контейнеры, не передаёт токены и не обращается к
письмам. Проверяются доверенный сертификат и имя хоста, отказы для недоверенного
сертификата и неверного имени, HTTP 401 без авторизации и ограничения nginx 403/404.
При ошибке сохранить вывод без содержимого секретных файлов. Успех не доказывает
проверку авторизованного JMAP, RBAC, provisioning, доставки, переноса или webmail.
На ноутбуке probe прошёл: TLS-сертификат и имя, оба отрицательных TLS-теста и
HTTP 401/403/404 — PASS. Это проверка Java probe из контейнера, а не тест
авторизованного адаптера Corvex или пользовательской сессии.

## Незавершённое создание ящиков

Подготовлены **выключенные по умолчанию** административный API и конфигурация,
журнал создания, доступ к James WebAdmin и получение primary account через JMAP.
При включении требуются отдельный mTLS-клиентский keystore и trust certificate,
файл секрета, JWT-ключ, явные origin и заранее созданные таблицы с проверяемыми
ограничениями. Пока соответствующего защищённого WebAdmin-прокси и безопасной
процедуры установки схемы нет — **не включать этот API**.

Сервис проверяет Spring JWT, текущее `ADMIN_USERS_MANAGE` и ACTIVE оператора и
владельца. Intent записывается до одной попытки создания; при неопределённом
исходе повтор запрещён, номер операции можно получить/проверить под исходным
оператором. После подтверждённого создания JMAP account ID записывается в
**выключенную** привязку; это не означает перевод webmail или доставки. Между
проверкой прав и удалённым вызовом остаётся гонка отзыва. Токен James даёт
полные права и не должен попадать в ответ или логи. Пароль создаваемого James
пользователя не сохраняется: перед включением протоколов потребуется отдельная
процедура credentials. Внутренний логин ограничен `localhost` и пока не связан
с реальным адресом доставки.

SQL-схемы находятся вне Flyway и не применяются автоматически. Нет готовой
миграции, операционного разрешения неопределённости, полноценного аудита и
разграничения привилегий БД. На временном PostgreSQL 16.9 проверены SQL-правила
конкуренции и ограничения, но Java/PostgreSQL IT ещё не выполнялись. На ПК
прошли прежние unit/mock тесты, включая сборку журнала и клиента; новые API,
конфигурация, mTLS, общий deadline и фильтр HTTP-логов ещё не прошли Maven и
live-проверки. HTTP wire/headers DEBUG с секретами должен быть выключен;
изменение уровня логирования во время запроса остаётся риском. Пользовательские
ящики не созданы, реальные письма не перенесены, почта не переключена.

## Подготовленный внутренний канал WebAdmin (ещё не проверен live)

Профиль `james-provision` добавляет в **тот же Compose** `james-admin` без
публикации порта. Он требует клиентский TLS-сертификат и допускает только PUT
для точно заданного сгенерированного `cvx-…@localhost`, без query/`force`, без
произвольных входных заголовков; все остальные пути и методы отклоняются.
До явного запуска этого профиля и выбора отдельного файла через
`CORVEX_JAMES_WEBADMIN_FILE` старый отключённый WebAdmin не меняется. Corvex API
provisioning остаётся по умолчанию выключенным. Дополнительные переменные Compose
могут вызвать пересоздание mail-storage при последующем обычном `compose up`.

`scripts/prepare-james-provision-laptop.ps1 -ConfirmLaptop` создаёт только
новые независимые ключи и файлы в Git-ignored `infra/secrets/james-provision` и
`infra/secrets/james-adapter`, отказывается от перезаписи и не запускает
Docker; при ошибке частичные файлы сохраняются. Keytool передаёт временные
пароли в аргументах, видимых локальному администратору. Установить ограничения
доступа и резервное копирование обоих каталогов; реальная ACL-защита Windows
пока не проверена. Полученные конфигурации — только ноутбук, не production.

`scripts/start-james-provision-bridge.ps1 -ConfirmLaptop` предназначен для уже
подготовленного ноутбука: проверяет работающий mail-storage с выключенным API и
healthy James PostgreSQL, пересоздаёт только James и его два прокси, ждёт JMX и
запускает mTLS-проверку. Он не переключает почту и не включает Corvex API. Тест
отправляет один **пустой PUT без Password** на синтетический логин и ожидает 401;
в James 3.9.1 валидное создание требует непустой JSON password. При сбое после
запуска не повторять генерацию ключей; сохранить вывод для диагностики.

Исходники James 3.9.1 показывают, что стандартный `LoggingRequestFilter` может
логировать тело запроса, однако `DataRoutesModules` регистрирует
`UserCreationRequestLogger`, который для PUT `/users` исключает тело с паролем.
Прокси требует строго канонический исходный URI, чтобы не обойти эту проверку.
Данный вывод сделан по исходному коду; реальные логи, конфигурация Nginx, mTLS и
права на файлы ещё не проверены на ноутбуке. После положительного transport
probe всё равно требуется отдельная проверка redaction с синтетическим значением
и аудит, прежде чем создавать реальные ящики. Связь прокси → James остаётся HTTP
внутри `james-internal` и не считается production-защитой.
