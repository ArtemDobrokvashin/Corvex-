# Перенос Corvex на тестовый сервер: план на неделю

Дата плана: **19.10.2026** (понедельник). Исходное состояние: `main` = `ad42ff2`,
ноутбук-стенд собран, `docker compose up -d --build` поднимает стек, миграции `V6`/`V8`
применяются. Цель недели — **работающий сервер с тестовым доменом, резервной копией,
проверенным восстановлением и включённой почтой на тестовых ящиках**, а не «production
для сотрудников».

> Главное правило недели: **каждый день заканчивается чем-то проверенным**. Лучше
> перенести в четверг с работающей почтой и восстановлением, чем в пятницу с
> неработающими напоминаниями. Пятница — резерв на сбой, а не на новые функции.

## Что считается успехом недели

- [ ] Сервер поднимает стек из `main` **на пустом диске** (не поверх старых volumes).
- [ ] Тестовый домен: сайт по HTTPS с валидным сертификатом, вход, админка, почта.
- [ ] Своя почта на тестовых ящиках: приём извне, отправка наружу, DKIM/SPF/DMARC проходят.
- [ ] Календарь: событие живёт на сервере и напоминание приходит письмом.
- [ ] Backup → restore на **отдельной** машине/диске проверен фактически.
- [ ] Есть план отката: предыдущий образ, предыдущий коммит, где лежит копия.
- [ ] Один отчёт `artifacts\smoke\acceptance-*.json` со статусом PASS, привязанный к SHA.

Не входит в неделю: общие календари, «Файлы», AD/LDAP, Outlook, второй компьютер,
рабочие ящики сотрудников, production MX.

## Что нужно от вас заранее (не блокирует код, но блокирует день 2)

| Нужно | Зачем | Когда |
|---|---|---|
| Тестовый домен (например `mail.test.example`), доступ к DNS | MX/SPF/DKIM/DMARC, сертификат | до дня 2 |
| Публичный IP + разрешённый **исходящий 25** у провайдера | внешняя доставка | до дня 3 |
| Сервер: Windows Server 2019/2022, 8 CPU / 16 ГБ / 500 ГБ SSD, статический IP | стек на 20 контейнеров | до дня 1 |
| Docker Desktop/Engine + JDK 17 + Maven 3.9 + Node 22 LTS на сервере | сборка на месте | день 1 |
| Отдельный внешний ящик для алертов | мониторинг не должен зависеть от самой почты | до дня 4 |
| Тестовые ящики: минимум 2 (например `i.ivanov`, `a.petrova`), без 2FA | сквозная почта и календарь | до дня 3 |

2FA у тестового пользователя **выключить на время приёмки**: `calendar_smoke.py` и
`mail_e2e.py` используют пароль, а не второй фактор. Это ограничение стенда, не
ослабление продукта: 2FA отдельно проверяется вручную в интерфейсе.

## Дни

### День 1 (пн, 19.10) — сборка и чистый старт

Цель: доказать, что `main` собирается целиком и поднимается **на пустых данных**.

1. На сервере: `git clone`, `git checkout main`, записать `git rev-parse HEAD` в журнал.
2. `scripts\first-run.ps1` — секреты, JWT-ключ, пилотный сертификат.
3. `.env`: домен, `CORVEX_INTERNAL_API_TOKEN` (один на все сервисы), пароль bootstrap-админа.
4. **Полный reactor — это G1:** `mvn -B clean verify`. Долго, но именно этого не хватало.
   Если красный — правим **первую** ошибку, остальные не трогаем.
5. Чистая установка: `docker compose up -d --build` на пустых volumes, `docker compose ps`.
6. `py -3 scripts\runtime_smoke.py --url https://... --report artifacts\smoke\runtime.json`.

Выход дня: Maven `BUILD SUCCESS` на точном SHA, все контейнеры `healthy`, runtime-smoke PASS,
SHA записан. Почта ещё выключена (`CORVEX_SMTP_ENABLED=false`).

### День 2 (вт, 20.10) — домен, TLS, вход, админка

1. DNS: `A` для `mail.<домен>`, `MX` на тестовый домен, `SPF`, `DKIM`, `DMARC p=none`.
2. Сертификат: сначала тестовый CA/Let's Encrypt staging, затем боевой.
3. Вход суперадмина, смена пароля, создание 2 тестовых пользователей и групп.
4. Проверить: админка, квоты, аудит; **доступ к чужой почте запрещён** (403/404).
5. `scripts\acceptance.ps1 -SkipMail -SkipCalendar` — toolchain + compose + runtime.

Выход дня: `https://mail.<домен>` открывается без предупреждений браузера, вход работает,
пользователи созданы, runtime PASS.

Если DNS ещё не готов — день не простаивает: делаем дни 4–5 на локальном стенде.

### День 3 (ср, 21.10) — почта на тестовом домене

1. Включить **только** `CORVEX_SMTP_ENABLED=true`, пересобрать/перезапустить затронутые
   сервисы, проверить `docker compose logs mail-smtp-service`.
2. Проверить приём: письмо с внешнего ящика → INBOX тестового пользователя в webmail.
3. Проверить отправку: webmail → внешний ящик; письмо с вложением; Bcc не раскрыт.
4. Негативные сценарии: несуществующий получатель → `550`; открытый relay запрещён;
   при остановленном `mail-storage-service` → `451`, а не ложный `250`.
5. `py -3 scripts\mail_e2e.py --sender ... --recipient ...` — SMTP + Sent + INBOX + вложение.
6. Доставляемость: SPF/DKIM/DMARC по заголовкам у внешнего получателя, mail-tester ≥ 9/10.

Выход дня: почта ходит в обе стороны, e2e PASS, DKIM подтверждён у внешнего получателя.

### День 4 (чт, 22.10) — календарь, чат, алерты

1. Календарь: `py -3 scripts\calendar_smoke.py --username ...` — событие, `409`,
   **письмо-напоминание**, удаление.
2. Ручная часть календаря (то, что не видит скрипт): второе окно/браузер, F5, зона
   `Europe/Amsterdam`, событие после перехода на летнее время.
3. Чат: два пользователя, direct и группа, чужой доступ, файл, EICAR, reconnect после Offline.
4. Алерты: `scripts\alert_e2e.py` — synthetic alert → письмо администратору.
5. `scripts\acceptance.ps1 -CalendarUser ... -Alert -AlertUser ...` — единый прогон.

Выход дня: один журнал `acceptance-*.json` без FAIL (допустимы обоснованные SKIP).

### День 5 (пт, 23.10) — backup, restore, откат, soak

1. `scripts\backup.ps1 -BackupRoot D:\CorvexBackup` — дампы, Maildir/CAS/chat, манифест SHA-256.
2. **Восстановление на чистой машине или отдельном диске:** `restore.ps1 -DataOnly` для
   тренировки, затем полный `restore.ps1 -Force` на изолированном стенде.
3. Сверить содержимое: письмо, вложение, папка, событие календаря, комната чата.
4. Откат: тег предыдущего образа, `docker compose up -d --build` на предыдущем коммите —
   убедиться, что процедура выполнима и занимает известное время.
5. Запустить 72-часовое наблюдение (до понедельника): очереди, DLQ, диск, память, bounce.

Выход дня: восстановление подтверждено фактически, откат проверен, soak идёт.

### Выходные — резерв

Если что-то поехало: суббота на исправление, воскресенье на повторный прогон
`acceptance.ps1` целиком и короткий итоговый отчёт. Никаких новых функций.

## Порядок включения, чтобы не сделать сервер недоступным

1. Сначала **веб** (443/80): если почта не поднялась, админка всё равно доступна.
2. Потом **SMTP 25/587**, затем **IMAP/POP3** — по одному, с проверкой после каждого.
3. `CORVEX_IMAP_ENABLED` / `CORVEX_POP3_ENABLED` включать **после** приёмки календаря и
   только если нужны клиенты: webmail работает без них.
4. Публичные порты БД (`5432`, `5672`, `6379`, `9200`) не открывать; `data`-сеть `internal`.
5. Перед каждым изменением `.env`: копия файла с датой. Откат `.env` — это тоже откат.

## Что делать, если день провален

| Симптом | Первое действие | Не делать |
|---|---|---|
| Maven красный на сервере, на ноутбуке зелёный | сравнить SHA и `java -version`/`mvn -version`, запустить один модуль | не понижать версии Spring/James «на всякий случай» |
| Flyway падает на пустом диске | прочитать первую ошибку миграции, проверить порядок `V1…V8` | не редактировать уже применённую миграцию |
| Контейнер в restart loop | `docker compose logs --tail 200 <сервис>`, искать `Caused by` | не удалять volumes |
| Письма не уходят наружу | проверить исходящий 25 у провайдера, PTR, SPF/DKIM | не переключать production MX «для теста» |
| Напоминание не приходит | `CORVEX_INTERNAL_API_TOKEN` одинаковый, `CORVEX_CALENDAR_FROM`, логи notification | не отключать проверку токена |
| 401 после входа | время/NTP, JWKS, разные JWT-ключи между перезапусками | не менять код авторизации на стенде |

## Артефакты недели

```
artifacts\smoke\
  runtime-<stamp>.json        состояние контейнеров и HTTPS
  mail-e2e-<stamp>.json       SMTP → INBOX → Sent + вложение
  calendar-<stamp>.json       событие, 409, напоминание, удаление
  alert-e2e-<stamp>.json      Alertmanager → письмо
  acceptance-<stamp>.json     сводка по шагам + SHA
  acceptance-<stamp>.log      полный журнал
D:\CorvexBackup\<stamp>\      дампы PostgreSQL, Maildir/CAS/chat, манифест SHA-256
```

`artifacts/` исключён из Git: отчёты остаются на сервере, в репозиторий попадают только
выводы. В отчётах нет паролей, токенов и содержимого писем — только статусы, длины и SHA.
