# Почтовый контур

Как Corvex принимает, хранит, отдаёт и отправляет почту; как подключить внешний ящик и
как устроен переход на Apache James. Общая схема конвейера — в
[`ARCHITECTURE.md`](ARCHITECTURE.md) §3. Состояние проверок — [`STATUS.md`](STATUS.md).

> **Почтовые протоколы по умолчанию выключены** (`CORVEX_SMTP_ENABLED`,
> `CORVEX_IMAP_ENABLED`, `CORVEX_POP3_ENABLED` = `false`). Это защита от потери письма,
> которое сервер принял, но не смог доставить. Включайте их только после приёмки.

## 1. Кто чем владеет

| Компонент | Ответственность |
|---|---|
| `mail-smtp-service` | приём SMTP (SubEtha), anti-open-relay на `RCPT`, submission 587 с AUTH и STARTTLS, DKIM, исходящая MX-очередь |
| `mail-storage-service` | durable spool, Maildir, метаданные, вложения CAS, квоты, правила, поиск, протокольный API для IMAP/POP3 |
| `mail-imap-service`, `mail-pop3-service` | протокольные машины Apache James 3.8.2 за портами-адаптерами; хранилище — через `mail-storage-service` |
| `mail-spam-service` | SPAMC → spamd, fail-open |
| `mail-antivirus-service` | INSTREAM → clamd, fail-closed по вложению |

Наличие James в зависимостях **не означает**, что James управляет текущим хранилищем:
`CorvexMailboxManager` и `CorvexMessageManager` обращаются к `mail-storage-service`.
Полный переход на James — отдельный этап, см. §6.

## 2. Входящее письмо

1. SMTP-сессия принимает `.eml` только для локальных доменов; посторонний релей
   отклоняется на `RCPT`.
2. Сырое письмо потоково пишется в durable spool; после этого отправителю уходит `250 OK`
   с `rawRef` для трассировки.
3. RabbitMQ разносит события: spam → AV → доставка в папку.
4. Хранилище проверяет квоту, применяет правила, пишет Maildir `tmp → new`, метаданные в
   PostgreSQL, вложения в CAS по SHA-256 и индексирует письмо.

Если storage или RabbitMQ недоступны, SMTP отвечает `451`, а не ложным `250 OK`:
отправитель повторит, письмо не потеряется. При недоступном ClamAV вложения блокируются,
при недоступном SpamAssassin письмо доставляется с пометкой.

## 3. Исходящее письмо

- Отправка из webmail публикует задание в очередь; SMTP-воркер подписывает письмо DKIM
  (rsa-sha256, relaxed/relaxed), находит MX и отправляет, повторяя временные ошибки до
  72 часов. Постоянный отказ даёт DSN.
- Submission 587 требует TLS и AUTH; при включённой 2FA принимается app-password, а не
  основной пароль. Чужой `MAIL FROM` отклоняется.
- Успешный ответ webmail означает приём в очередь, а не подтверждённую доставку. Копия в
  Sent сохраняется отдельно, поэтому `sentMessageId` может быть `null`.
- Ключа идемпотентности у `/mail/messages/send` нет: при тайм-ауте повтор может создать
  дубликат. Не переиспользуйте один запрос как «безопасный retry».

Доставляемость — не свойство кода: нужны PTR, SPF, DKIM, DMARC, прогрев IP и mail-tester
≥ 9/10. Чек-лист — [`TESTING.md`](TESTING.md), DNS — [`INSTALL.md`](INSTALL.md) шаг 7.

## 4. Хранение и квоты

- Тело письма — `.eml` в Maildir, запись через `tmp → new` (атомарно).
- Вложения — контентно-адресуемый склад: файл хранится один раз на всех получателей.
- Метаданные, флаги, `UID`, `MODSEQ` — PostgreSQL. `UID` и `MODSEQ` выделяются из одной
  заблокированной строки папки и двигаются на `APPEND`/`COPY`/`MOVE`/флагах/`expunge`.
- Квота по умолчанию — 5 ГиБ на ящик, меняется в админке без перезапуска. 90 % — письмо
  владельцу, 100 % — временный отказ входящим, а не потеря письма.
- Папки в Maildir используют санитизированные имена, а не идентификаторы. Одинаковые по
  длине кириллические имена могут дать один путь, поэтому создание и переименование
  сериализуются на уровне владельца и возвращают `409` при конфликте. Это известное
  ограничение; переход на стабильные идентификаторы — отдельная работа.

## 5. Протоколы

| Протокол | Порты | Состояние |
|---|---|---|
| SMTP приём | 25 | реализован, выключен по умолчанию |
| Submission | 587 (AUTH + STARTTLS) | реализован, ограниченный живой smoke пройден |
| IMAP | 143 (STARTTLS), 993 (implicit TLS) | реализован на James; `MOVE`, `QUOTA`, `CONDSTORE`; подписки `LSUB` пока в памяти процесса |
| POP3 | 110, 995 | реализован; `UIDL` стабилен, `DELE` на `QUIT`; согласованный Thunderbird-smoke 995 пройден |

Внутри контейнера порты непривилегированные, наружу Docker публикует стандартные.
Проверка пароля и app-password идёт через `auth-service`; при его недоступности протокол
не должен трактовать ошибку как «неверный пароль» — это отдельно проверяется в приёмке.

## 6. Переход на Apache James

В `docker-compose.yml` есть **выключенный по умолчанию** профиль `james-transition`
(`james`, `james-postgres`, `james-jmap` как внутренний TLS-прокси) и профиль
`james-provision`. У них отдельные тома и внутренняя сеть; внешние порты не публикуются,
и существующие маршруты не изменены. Обычный `docker compose up` эти контейнеры не
поднимает.

Что уже проверялось: сборка профиля, синтаксис конфигурации, `ListDomains`, транспорт
`Corvex → james-jmap` без авторизации, чтение после штатного пересоздания контейнера.
**Это не подтверждает** доставку, протоколы, права, отзыв доступа и восстановление.

До включения профиля требуется:

1. **Один источник истины.** James владеет своими данными; Corvex не пишет напрямую в
   файлы и таблицы James. Двойной записи быть не должно.
2. **Provisioning и права.** Доверенный реестр ящиков, проверка актуального RBAC и отзыв
   доступа; `webadmin` включён осознанно, а не «для удобства».
3. **Поиск и storage.** Режим `scanning` годится только для ноутбука; для сервера нужна
   поддерживаемая конфигурация.
4. **AV и spam** в пути James, а не только в старом конвейере.
5. **Остановка всех писателей, сверка и обратный путь** для писем, пришедших в момент
   переключения.
6. **Проверенное восстановление** обоих новых томов: отдельный том — не резервная копия.

Пока эти пункты не закрыты, профиль остаётся кандидатом инфраструктуры. Не помещайте в
него реальные письма и не запускайте `docker compose down -v`.

## 7. Внешние ящики

Коннектор подключает существующий ящик сотрудника (Mail.ru, Яндекс, Gmail, Outlook или
свой сервер по IMAP/POP3). Нужен там, где адрес исторически живёт у провайдера, а
переписку нужно постепенно перенести в Corvex.

- Пресеты провайдеров и custom IMAP/POP3/SMTP; проверка входящего подключения и SMTP без
  отправки письма.
- Сбор новых писем по расписанию и одноразовый импорт архива IMAP-папок с датами и
  флагами `\Seen`, `\Answered`, `\Flagged`, `\Draft`, если источник их отдаёт.
- Дедупликация по `UIDVALIDITY`+UID, POP3 `UIDL`, `Message-ID` и SHA-256 сырого `.eml`.
- Собранная почта проходит обычный конвейер: spam → AV → Maildir → поиск.
- Отправка от имени внешнего адреса через authenticated SMTP провайдера, копия в Sent
  Corvex и попытка `APPEND` в Sent провайдера для IMAP.
- Вход через Google и Microsoft 365 (OAuth 2.0, authorization code + PKCE): Microsoft 365
  иначе недоступен вообще, а в рабочих доменах Google app passwords часто запрещены.
  OAuth работает для IMAP-источников; отправка через OAuth-ящик пока отвечает `409`.
- Статусы, история запусков, ручная синхронизация, пауза, сброс курсоров.
- Право `MAIL_EXTERNAL_ACCOUNTS`, аудит, секрет в AES-256-GCM.

Ключ шифрования — `CORVEX_EXTERNAL_MAIL_ENC_KEY`, генерируется `first-run.ps1`. Его потеря
означает повторное подключение ящиков, поэтому `.env` входит в резервную копию. Политика
по умолчанию: `ALLOW_PRIVATE_NETWORKS=false`, `ALLOW_INSECURE_PLAIN=false`, не более
10 ящиков на пользователя.

Вход через провайдера включается переменными окружения mail-storage-service:

| Переменная | Значение |
|---|---|
| `CORVEX_OAUTH_GOOGLE_CLIENT_ID`, `CORVEX_OAUTH_GOOGLE_CLIENT_SECRET` | приложение в Google Cloud; redirect URI `https://<адрес>/api/v1/mail/external-accounts/oauth/callback` |
| `CORVEX_OAUTH_MICROSOFT_CLIENT_ID`, `CORVEX_OAUTH_MICROSOFT_CLIENT_SECRET` | приложение в Azure; тот же redirect URI |
| `CORVEX_OAUTH_MICROSOFT_TENANT` | `common`, `organizations` или идентификатор тенанта; по умолчанию `common` |
| `CORVEX_PUBLIC_BASE_URL` | внешний адрес приложения без хвостового `/`; из него собирается redirect URI. Без домена годится `http://localhost:8080` — провайдеры принимают loopback |
| `CORVEX_OAUTH_TIMEOUT_SECONDS` | таймаут запросов к провайдеру, 5–60, по умолчанию 15 |
| `CORVEX_OAUTH_STATE_TTL_MINUTES` | срок жизни `state`, 1–30, по умолчанию 10 |
| `CORVEX_OAUTH_CONNECTION_TTL_MINUTES` | сколько согласие ждёт создания ящика, 5–120, по умолчанию 30 |

Если для провайдера не заданы client id и secret или пуст `CORVEX_PUBLIC_BASE_URL`, кнопка
входа показывается неактивной, а `POST /oauth/authorize` отвечает `503`. Токены хранятся
только шифртекстом (`external_mail_oauth_tokens`), в журнал не попадают. При отзыве
согласия провайдер отвечает `invalid_grant`: ящик получает `reauthRequired`, сбор
останавливается, в интерфейсе появляется «войдите заново» вместо повторяющихся 401.
Повторный вход заменяет токены у того же ящика (`PUT /mail/external-accounts/{id}` с
`oauthConnectionId`): настройки, курсоры папок и журнал перенесённых писем сохраняются,
поэтому повторного импорта и дублей не будет.

### Что переносит импорт архива

`POST /mail/external-accounts/{id}/migrate` (в интерфейсе — **«Импорт архива»**) запускает
одноразовый проход по всем папкам IMAP-источника:

- структура папок повторяется как есть, специальные папки (`Sent`, `Drafts`, `Trash`,
  `Junk`, `Archive`) сопоставляются системным;
- сохраняются дата письма и флаги `\Seen`, `\Answered`, `\Flagged`, `\Draft`, если источник
  их отдаёт;
- вложения не разбираются по частям: сырой `.eml` целиком уходит в обычный конвейер
  spam → AV → Maildir → индекс, поэтому вложения и структура MIME сохраняются;
- дубликаты отсекаются по `UIDVALIDITY`+UID, POP3 `UIDL`, `Message-ID` и SHA-256: обрыв
  соединения не теряет прогресс, а повторный запуск пересканирует папки с начала, пропуская
  уже перенесённые письма;
- по завершении можно оставить обычный сбор новых писем.

Настройка выполняется владельцем ящика, а администратор с `ADMIN_MAIL_POLICY` может завести
подключение за сотрудника (`targetUserId`).

### Перенос заданием: preview, пауза, отчёт

Одноразовый импорт поверх уже настроенного подключения оформлен как задание
`/mail/migration` — отдельная сущность со своим планом и очередью:

- `POST /mail/migration/preview` — оценка объёма до старта. Источник открывается только на
  чтение: папки, число писем, размер по выборке до 50 писем на папку, остаток квоты.
  Сразу видно, помещается ли архив: «Архив 12,4 ГБ · квота 5 ГБ · не поместится 7,4 ГБ».
- `POST /mail/migration` — создать задание. План сохраняется по папкам, второе активное
  задание по тому же ящику отклоняется.
- `POST /mail/migration/{id}/pause | resume | cancel` — управление. Пауза останавливает
  после текущего письма и сохраняет курсор папки, поэтому продолжение не перечитывает
  архив заново.
- `GET /mail/migration/{id}/report` — отчёт по папкам: оценка, перенесено, пропущено,
  ошибка и остаток квоты.

Миграция идёт в отдельном пуле `corvex-mail-migration` (2 потока) и не занимает
`schedulerThreads` постоянного сбора: новая почта приходит, пока переносится архив.
У Gmail по умолчанию пропускаются `All Mail`, `Important` и `Starred` — иначе каждое
письмо попало бы в архив дважды; включить их можно осознанно в запросе.

Интерфейса мастера и админской сводки пока нет: это этапы 2 и 3 плана
[`MIGRATION.md`](MIGRATION.md). API работает, но проверен только тестами и разбором кода —
живого прогона на реальном архиве не было.

### Чего импорт не делает

- **Не является двусторонней синхронизацией.** Прочтение, удаление и перемещение в старом
  ящике не переносятся в Corvex и обратно; после переноса старый ящик живёт своей жизнью.
- **Не переносит ничего, кроме почты.** Календарь, задачи, правила, подписи и настройки
  старого сервиса остаются там. Контакты переносятся отдельно и не из старого ящика, а из
  выгрузки сервиса: `.vcf` или `.csv` через **«Адресную книгу»** — см.
  [`USER-GUIDE.md`](USER-GUIDE.md).
- **Не обходится одним паролем приложения.** Microsoft 365 подключается только входом
  через Microsoft: basic auth отключён с 2022 года, пароли приложений не работают. Gmail
  подключается входом через Google или паролем приложения при 2FA; Яндекс и Mail.ru —
  паролем приложения. Если администратор провайдера запретил IMAP, перенос не пойдёт ни
  тем, ни другим способом — это ограничение источника.
- **POP3 переносит только INBOX** — без папок и без истории за пределами ящика.
- **Не является атомарным.** Оборванный запуск оставляет состояние `PARTIAL`; повтор
  продолжит работу, но часть писем может быть уже доставлена, а часть ещё нет.

Задержка обычного сбора зависит от интервала polling: в проверенном smoke письмо Mail.ru
появилось через 1–2 минуты. Realtime-доставка требует устойчивого IMAP IDLE с reconnect и
fallback — это следующий этап.

Проверено живьём: ongoing-сбор Mail.ru и Яндекса без дублей, app-password, polling.
Не проверено: импорт архива на ~6550 писем, Gmail/Outlook/custom, полная миграция с
вложениями и флагами, продолжение после обрыва на большом объёме. До этой приёмки импорт
архива — рабочая функция без подтверждённого результата, а не гарантированный перенос.
Подробные команды и ограничения — [`TESTING.md`](TESTING.md).

## 8. Сценарии развёртывания

| Сценарий | Приём | Отправка | Когда подходит |
|---|---|---|---|
| Ящики у провайдера, Corvex как единый интерфейс | провайдер → сбор по IMAP/POP3 | SMTP провайдера с его авторизацией | переходный период, адреса на чужих доменах |
| Почта на собственном сервере Corvex | MX → Corvex, порт 25 | MX получателя напрямую, DKIM | целевая схема после приёмки |
| Смешанная схема | часть доменов у провайдера, часть локально | по домену получателя | постепенный перевод подразделений |

Переключатель `CORVEX_MAIL_EXTERNAL_PROVIDER_ONLY` по умолчанию `false`. При явном
включении отправка из подключённого внешнего ящика идёт через SMTP провайдера даже для
адресов локального домена. Это нужно, когда фактическим владельцем доменных ящиков
остаётся провайдер. Переключатель общий, split delivery не поддерживает и сквозной
проверки не проходил — в рабочей среде не включать.

Покупка домена сама по себе не создаёт ящики: она даёт только имя и DNS.

## 9. Надёжность переноса писем

Перенос `.eml` и обновление строки БД не являются одной атомарной операцией. Известные
границы:

- `moveMessage` перемещает файл до коммита транзакции; при неудачном коммите запись может
  указывать на старый путь;
- групповая операция при ошибке на одном письме может успеть перенести часть;
- потерянный HTTP-ответ не говорит клиенту, выполнен ли перенос, поэтому слепой повтор
  недопустим;
- на локальном стенде в ноябре 2026 найдены письма, чьи файлы отсутствовали по путям
  метаданных; исходники восстановлены из копии, побайтово одинаковые копии лежат в
  `Trash`. Причина не доказана.

Промежуточная реализация (копия через `storeMessage` с fsync, удаление оригинала по
commit, удаление копии по rollback, блокировки целевой папки и строки письма) **не
является журналом восстановления**: при падении процесса возможны сиротские копии, а
взаимодействие с `EXPUNGE`/POP3 и конкуренция не проверены.

Практические правила до появления журналируемого переноса:

- не выполнять массовые переносы и удаления на стенде с нужными письмами;
- не удалять найденные «лишние» копии и файлы — сначала разбор;
- при неизвестном результате операции зафиксировать идентификаторы и остановиться, а не
  повторять запрос;
- перед любыми работами — проверенная резервная копия ([`OPERATIONS.md`](OPERATIONS.md)).

## 10. Что проверить перед включением

Собственный сквозной SMTP-сценарий, негативные ответы (`550` на неизвестного получателя,
запрет open relay, `451` при недоступном storage), EICAR и недоступность ClamAV, DKIM/SPF/
DMARC у внешнего получателя, IMAP и POP3 в Thunderbird и Outlook, повтор без дубля,
переживание рестарта. Полный чек-лист — [`TESTING.md`](TESTING.md).
