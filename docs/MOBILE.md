# Мобильный клиент: состояние и что нужно до MVP

Каркас Android-приложения живёт в каталоге `android/`, контракт для iOS — в
`MOBILE_IOS_CONTRACT.md` (в `docs/`). Готовится в ветке `arena/b9fa12e4-corvex`, PR #205:
**27 файлов, +1239 строк**, все три задания CI зелёные.

**Что этот документ утверждает:** мобильный код **ни разу не собирался** — ни в CI, ни
локально. Зелёный CI к нему отношения не имеет: задание `Java 17 / Maven reactor` собирает
только Maven-модули из `services/`, каталог `android/` в reactor не входит. Поэтому «каркас
готов» здесь означает «файлы написаны», а не «приложение запускается».

Правило прежнее: пока нет команды и вывода — это не проверка. Всё, что ниже в разделе 3,
найдено чтением кода, а не прогоном.

## 1. Что уже написано

| Слой | Файлы | Состояние |
|---|---|---|
| Сеть | `NetworkModule`, `BaseUrlInterceptor`, `AuthInterceptor`, `AuthCookieJar` | динамический адрес сервера, подстановка Bearer, refresh по `401`, cookie-jar для refresh |
| Безопасность | `SecureStorage` | `EncryptedSharedPreferences`, ключ `AES256_GCM`; токен и адрес сервера вне `UserDefaults`-аналога |
| Авторизация | `AuthApi`, `AuthRepository`, `LoginScreen`, `LoginViewModel` | вход по паролю, ветка MFA/TOTP, разбор `ProblemDetails` в текст ошибки |
| Почта | `MailApi`, `MailRepository`, Room (`CorvexDatabase`, `MailDao`, `MailEntity`) | список папок и писем, локальный кэш |
| Фон | `MailSyncWorker` | периодическая задача каждые 15 минут, `NetworkType.CONNECTED` |
| Чат | `StompClient` | `CONNECT` / `SUBSCRIBE` / `SEND` / `DISCONNECT` поверх `wss://<host>/ws` |
| Календарь | `CalendarApi` | только интерфейс API, экрана и репозитория нет |
| Предпросмотр | `PdfPreviewScreen` | `PdfRenderer` для PDF из вложения |
| iOS | `MOBILE_IOS_CONTRACT.md` | Keychain, `URLSession`, pinning по SPKI, `BGAppRefreshTask`, схема БД, STOMP |

Что сделано правильно и стоит сохранить:

- refresh идёт **отдельным** `OkHttpClient` без `AuthInterceptor` — то есть мобильный клиент
  не повторяет дефект веб-клиента, найденный 20.11 (#182), где просроченный Bearer прикреплялся
  к самому `/auth/refresh` и обновление не могло сработать в принципе;
- логин исключён из подстановки Bearer;
- токен лежит в `EncryptedSharedPreferences`, а не в обычных настройках;
- `android:allowBackup="false"` — резервное копирование приложения не утащит токен.

## 2. Чего нет (и без чего MVP не начинается)

1. **Gradle wrapper.** Нет `gradlew`, `gradle/wrapper/*`. Собрать можно только локальным
   Gradle нужной версии; воспроизводимости нет.
2. **`gradle.properties`.** Нет `android.useAndroidX=true` и `org.gradle.jvmargs`. С AGP 8 и
   AndroidX-зависимостями сборка падает на этом флаге.
3. **`proguard-rules.pro`.** Указан в `app/build.gradle.kts` для release, файла нет.
4. **CI для Android.** Ни одного задания. Пока его нет, «зелёный CI» не значит «собирается».
5. **Ни одного запуска на устройстве или эмуляторе**, ни одного скриншота.
6. **Живого бэкенда.** Ни один экран не проверялся против `corvex-fresh`.
7. **Календаря как экрана**, пуш-уведомлений, офлайн-очереди, iOS-приложения.

## 3. Найденные дефекты

Порядок — по последствиям. Все найдены чтением; ни один не подтверждён прогоном, потому что
прогона не было.

### P0. Приложение не соберётся

Отсутствие `android.useAndroidX=true` и wrapper'а — не «неудобство», а гарантированная ошибка
на первом же `gradlew assembleDebug`. Первый шаг до MVP — не экраны, а **собирающийся проект**.

### P0. Тест не проверяет то, что написано в его имени

`AuthInterceptorTest` называется «401 triggers refresh and retries request with new token», но
`AuthInterceptor` в нём **не создаётся**. Тест трижды вручную дергает `MockWebServer` и
проверяет коды ответов; ни `SecureStorage`, ни перехватчик не участвуют. Любая регрессия в
`AuthInterceptor` (например, возврат к подстановке Bearer в `/auth/refresh`) пройдёт мимо.

Это ровно тот класс, за который мы уже заплатили в `restore_verify.ps1`: «зелёно» есть,
проверки нет. Лечится тестом, который создаёт настоящий перехватчик с подставным хранилищем.

### P1. Certificate Pinning выключен по умолчанию и падает при неверном формате

`NetworkModule.provideCertificatePinner`:

```kotlin
if (!host.isNullOrBlank() && !pin.isNullOrBlank()) {
    builder.add(host, pin)
}
```

Три проблемы:

1. **Пустой пин = нет пина.** `CertificatePinner` без правил ничего не проверяет сверх
   системного хранилища, а PR сообщает «Certificate Pinning». Молчаливый fail-open.
2. **Формат не проверяется.** OkHttp ждёт `sha256/<base64 SPKI>`; поле называется
   `pinnedCertSha256` (сертификат, а не публичный ключ). Hex-строка или base64 без префикса
   даст `IllegalArgumentException` в момент создания клиента — приложение упадёт на старте
   с непонятной ошибкой.
3. **Пин вводит пользователь** на том же экране, что и адрес сервера. Если адрес выбирает
   атакующий, он же выберет и пин. Пин имеет смысл только из доверенного канала: QR-код или
   конфиг, подписанный администратором.

### P1. Refresh-cookie уходит на каждый запрос

`AuthCookieJar.loadForRequest` возвращает cookie с `path("/")` для любого запроса к хосту,
а `Max-Age`, `Expires` и `SameSite` при сохранении теряются. То есть refresh-токен едет в
каждом `GET /api/v1/mail/...`, хотя нужен только на `/api/v1/auth/`.

Правильно: отдельный cookie-jar для refresh-клиента или путь `/api/v1/auth/`, и сохранение
срока жизни. Сейчас это расширяет поверхность атаки без всякой пользы.

### P2. Разбор хоста ломает IPv6

`removePrefix(...).substringBefore("/").substringBefore(":")` на адресе
`https://[2001:db8::1]:8443` даст `[2001` — пин привяжется к несуществующему хосту и просто
не сработает (ещё один fail-open). Нужен `HttpUrl.parse(...)?.host`.

### P2. Фоновая синхронизация — заглушка

`MailSyncWorker.doWork()` возвращает `Result.success()` и не делает ни одного запроса.
Задача при этом планируется каждые 15 минут. В системе координат Android это «синхронизация
успешно завершена» без синхронизации — идеальный способ месяц не замечать, что почта не
обновляется.

### P2. STOMP без heartbeat и переподключения

`StompClient` шлёт `heart-beat:10000,10000`, но не отправляет переводы строк каждые 10 секунд
и не отвечает на серверные. Брокер закроет соединение по таймауту. Нет переподключения,
нет ожидания `CONNECTED` перед `SUBSCRIBE` (гонка), нет разбора кадров — `onMessage` отдаёт
сырой текст. `clientMessageId` из iOS-контракта не используется, хотя он нужен для
идемпотентности повторов.

### P2. Чистый HTTP на Android 8

`minSdk = 26`, а `android:usesCleartextTraffic` не задан: на Android 8.0/8.1 незашифрованный
трафик разрешён по умолчанию. Пользователь, введя `http://`, получит передачу пароля
открытым текстом. Нужно `usesCleartextTraffic="false"` плюс `networkSecurityConfig` для
отладки.

### P3. Адрес сервера сохраняется до успешного входа

`AuthRepository.login` пишет `secureStorage.serverUrl` до запроса, поэтому опечатка остаётся
активной базой и следующий запуск начинается с нерабочего адреса. Писать после успеха.

### P3. Расхождение с iOS-контрактом

В контракте пиннинг описан как SHA-256 **публичного ключа** (SPKI), в Android поле называется
`pinnedCertSha256`. Две платформы будут проверять разные вещи. И в контракте не сказано
главное правило из #182: запрос `/auth/refresh` не должен нести просроченный Bearer.

## 4. Порядок до MVP

Первый пункт не двигается: без него остальное не проверить.

1. **Собирается.** Wrapper, `gradle.properties`, `proguard-rules.pro`, `assembleDebug` на
   чистой машине. Отдельное задание CI: `./gradlew test assembleDebug`.
2. **Честный тест перехватчика.** Создаётся настоящий `AuthInterceptor` с подставным
   хранилищем; проверяются: Bearer подставляется, на `/auth/login` не подставляется, при `401`
   идёт один refresh и один повтор, при провале refresh токен очищается.
3. **Пиннинг по-настоящему.** Формат `sha256/<base64>`, валидация при вводе, явная ошибка
   вместо молчаливого отключения, `HttpUrl.host`, пин из QR/подписанного конфига.
4. **Cookie только на auth-пути** и с сохранением срока жизни.
5. **Живой вход** против `corvex-fresh`: пароль, TOTP, refresh через 15 минут (тот самый
   сценарий из #182), выход.
6. **Почта**: папки, список, чтение, отметка о прочтении; синхронизация с курсором `cursorUid`.
7. **Чат**: heartbeats, переподключение, `clientMessageId`.
8. **Календарь** (сейчас только API), **PDF** на реальном вложении.
9. **Проверка на устройстве**: Android 8.0 (minSdk), Android 14 (targetSdk), тёмная/светлая
   тема не требуется — интерфейс светлый по правилу проекта.
10. **Только потом** iOS по контракту, с исправленным пунктом про SPKI и refresh.

## 5. Правила, чтобы мобильная часть не потерялась

- Каталог `android/` и `MOBILE_IOS_CONTRACT.md` не удаляются и не перезаписываются при
  слияниях; изменения в `services/` и `android/` живут вместе.
- `git push --force` в ветку мобильного клиента не делается. Если нужен rebase — обычный
  merge из `main`.
- PR #205 не закрывается и не пересоздаётся: он остаётся точкой входа в мобильную работу,
  пока каркас не сведён в `main`.
- После сведения в `main` появляется страж: тест проверяет, что `android/app/build.gradle.kts`,
  manifest и контракт на месте. До слияния такой тест держать нельзя — он был бы красным
  на `main`.

## 6. Чего этот документ не доказывает

Он составлен чтением кода 21.11.2026 и не заменяет ни сборку, ни запуск. Пункты «не
собирается» и «тест ничего не проверяет» проверяются одной командой каждый — и это первые
две команды, которые нужно выполнить, когда появится окружение с Android SDK.
