# Полный аудит Corvex — октябрь 2026

**Дата:** 19 октября 2026 года  
**Объект:** фронтенд, 12 Java-сервисов, Docker Compose, nginx, скрипты первого запуска и резервного копирования, OpenAPI-контракты и эксплуатационная документация.  
**База аудита:** ветка `arena/3732db07-corvex`, состояние после Stage 1 и редизайна Quiet Work, с исправлениями этого аудита.  
**Статус документа:** инженерный аудит готовности и реестр остаточных рисков. Он не заменяет нагрузочное тестирование, пентест и приёмку на Windows Server с Docker.

---

## 1. Краткий вердикт

Corvex уже можно рассматривать как **рабочий внутренний пилот Stage 1**: локальный вход, MFA, refresh-сессии, пользователи, группы, RBAC, аудит и настройки связаны реальными API. Интерфейс полностью переведён на русский и английский, а ключевые ошибки API теперь локализуются и на сервере по `Accept-Language`.

Corvex **нельзя пока выводить в боевую почту или обещать как готовую замену Exchange**:

1. SMTP-доставка и постоянное хранение писем относятся к Stage 2 и ещё не завершены.
2. IMAP/POP3 пока являются портами и контейнерами без подключённых протокольных движков Apache James.
3. Чат не сохраняет сообщения и не проверяет членство в комнатах — это Stage 4.
4. Java-код в аудиторской песочнице не удалось скомпилировать: нет JDK, Maven и Docker. Первый обязательный шаг на чистой машине — `mvn test` по каждому сервису и `docker compose up --build` со smoke-сценарием.
5. Spring Boot 3.2.5 уже вне открытой поддержки. Перед публичным production нужен отдельный, протестированный апгрейд Spring Boot/Spring Cloud.

Главный результат аудита — не только список проблем. Критичные дефекты Stage 1, которые можно было исправить без изменения дорожной карты, исправлены сразу: межсервисный API получил токен, IP за nginx перестал подделываться, SMTP стал fail-closed на всех уровнях, последнего SUPER_ADMIN больше нельзя случайно удалить из системы, а фронтенд получил полноценные RU/EN и безопасную работу с emoji.

## 3. Что исправлено в ходе аудита

### 3.1. Двуязычный интерфейс RU/EN

- Единый словарь в `frontend/src/i18n/index.tsx`; русская строка является ключом, поэтому отсутствующий перевод легко искать автоматически.
- Язык определяется из сохранённого выбора, затем из языка браузера; RU — безопасный fallback.
- Выбор сохраняется в `localStorage`, обновляет `<html lang>` и заголовок вкладки.
- Переключатель RU/EN есть на входе, в боковой навигации и в профиле.
- Даты, время, числа, байты и русские/английские плюральные формы форматируются через `Intl` и локаль-зависимые правила.
- Системные имена шести групп локализуются; пользовательские имена и названия подразделений не переводятся насильно, потому что это данные компании.
- Демо-письма, комнаты и сообщения имеют стабильные ID и английские зеркальные наборы; локально отправленные пользователем сообщения при смене языка не теряются.
- HTTP-клиент отправляет текущий `Accept-Language` при каждом запросе и при refresh.

### 3.2. Локализация backend API

- В auth-service и admin-service добавлены `ApiMessageLocalizer` на HTTP-границе.
- Доменная логика по-прежнему использует канонические русские сообщения и логи; перевод выполняется только для публичного `ProblemDetail`.
- Покрыты точные сообщения, префиксы с логином/e-mail/группой, динамический lockout, политика пароля, Bean Validation и префиксы полей вида `username: ...`.
- Добавлены `AcceptHeaderLocaleResolver` с поддержкой RU/EN и русским fallback.
- Admin-service пробрасывает локаль в auth-service и повторно локализует ошибки на своей границе.
- Фронтендный mapper ошибок оставлен как defense-in-depth для старых или неполных ответов.
- Добавлены unit-тесты обоих локализаторов. Они написаны, но в этой среде не запускались из-за отсутствия JDK/Maven.

### 3.3. Emoji и Unicode

- Добавлен собственный компактный emoji picker без картинок и CDN: emoji остаются обычным Unicode-текстом, копируются, индексируются и проходят через JSON без преобразования.
- Вставка происходит в позицию курсора/выделения; после вставки фокус и каретка восстанавливаются.
- Добавлен графемно-безопасный текстовый слой: инициалы, обрезка сниппетов и Markdown-preview не режут surrogate pairs, skin-tone modifiers, keycap, variation selectors, ZWJ-последовательности и флаги.
- Каталог picker специально ограничен старыми, преимущественно односимвольными emoji. Флаги и ZWJ-профессии убраны: штатные шрифты Windows не рисуют флаги стран, а fallback Windows 7 заметно беднее современных emoji-шрифтов.
- Пользовательские сложные emoji при вставке из буфера не разрушаются; их глиф зависит от ОС. Это честное ограничение нативного подхода.
- CSS получил стек `Segoe UI Emoji`, `Segoe UI Symbol`, `Noto Color Emoji`, `Apple Color Emoji` и системные fallback.
- Тесты покрывают сегментацию, вставку, UTF-8 длину и сохранение emoji при очистке Markdown-preview.

### 3.4. Фронтенд: сессии, ошибки и доступность

- Refresh access token сделан single-flight: параллельные 401 больше не запускают несколько ротаций refresh-cookie и не могут ложно разлогинить пользователя.
- Ошибки `ProblemDetail` централизованы и локализуются; сетевые и HTTP-ошибки различаются.
- STOMP-клиент защищён от битого JSON и не падает на неожиданном теле кадра.
- Временный пароль в форме создания пользователя больше не отображается открытым текстом.
- Исправлена вложенная интерактивность строки письма: клавиатурный путь теперь даёт настоящая кнопка темы, а звезда остаётся отдельным контролом.
- Поисковые поля получили `aria-label`.
- Внешние Markdown-изображения в чате запрещены санитайзером: tracking pixel не должен сообщать третьим лицам IP сотрудника и время чтения. Будущие файловые вложения должны рендериться доверенным компонентом, а не произвольным `<img>` из Markdown.

### 3.5. Backend и безопасность

- JWT теперь содержит документированный claim `groups` наряду с `permissions`.
- Восстановление RSA public key использует реальный public exponent CRT-ключа, а не всегда 65537.
- Gateway разрешает cookie-based `/logout` без ещё живого access token: пользователь с истёкшим access, но валидной refresh-сессией может корректно выйти.
- Повторный TOTP setup при уже включённой 2FA запрещён. Украденный access token больше не может одной операцией заменить секрет и фактически отключить второй фактор без текущего кода.
- Внутренние `/internal/**` auth/admin защищены fail-closed фильтром `X-Corvex-Internal-Token`:
  - пустой секрет → `503`, а не открытый API;
  - неверный секрет → `401`;
  - сравнение выполняется через `MessageDigest.isEqual`;
  - секрет обязателен в Docker Compose и генерируется `first-run.ps1`;
  - существующим установкам скрипт добавляет только недостающую переменную, не переписывая остальные секреты.
- Клиентский IP за доверенным nginx больше не берётся из первого, подделываемого элемента `X-Forwarded-For`. nginx перезаписывает `X-Real-IP` и `X-Forwarded-For` из TCP-адреса; gateway rate limiter, auth и admin используют доверенный `X-Real-IP`, затем последний XFF и только потом remote address.
- Gateway и STOMP origins берутся из `CORVEX_WEB_ORIGINS`, а по умолчанию выводятся из `https://${CORVEX_DOMAIN}`. Пустое значение в `.env` не ломает fallback благодаря вложенной интерполяции Compose.
- SMTP listener теперь выключен по умолчанию одновременно в Java, `application.yml` и Compose. Нельзя случайно подтвердить отправителю `250 OK`, пока сырое письмо теряется в заглушке.
- Последнего члена `SUPER_ADMIN` нельзя лишить группы, заблокировать или отключить через публичный admin API.
- PATCH настроек сначала валидирует и нормализует весь набор, затем пишет одной транзакцией. Числа, диапазоны и boolean проверяются на сервере, а не только в браузере.
- Гонка двух create-запросов, упёршаяся в UNIQUE/FK, теперь возвращает локализованный `409 Conflict`, а не `500` и не SQL-текст.
- `MaildirStorage` действительно выполняет `force(true)` перед rename, создаёт root вложений до temp-файла, чистит temp при сбоях и корректно обрабатывает гонку одинаковых вложений.
- Webhook Alertmanager больше не делает unchecked cast для `labels`/`annotations`: malformed payload не роняет обработчик `ClassCastException`.
- STOMP skeleton отклоняет пустого principal, невалидный UUID субъекта и пустое тело до Stage 4.

## 4. Реестр остаточных находок

### P0 — блокеры боевого запуска

#### P0-01. Java и Docker ещё не проходили реальную сборку в этой среде

**Риск:** синтаксическая ошибка, несовместимость Spring-бинов, Flyway или healthcheck обнаружится только на первом хосте.  
**Gate:** JDK 17 + Maven `test`, затем Docker build/up и smoke. До этого нельзя называть сервисы «здоровыми».

#### P0-02. Почтовый конвейер Stage 2 не завершён

> **Обновление после аудита (Stage 2A):** inbound-половина закрыта в коде — durable raw spool,
> потоковый лимит, exchange/queues/DLQ, spam/AV consumers, MIME/Maildir/CAS/квоты/ES и
> read-side webmail API. Открытыми остаются runtime-smoke на JDK/Docker-хосте и Stage 2B:
> submission AUTH/TLS, исходящая очередь retry/DSN и DKIM/SPF/DMARC-проверка на пилоте.

- `RawMessageStoreClient` возвращает UUID, но не сохраняет `.eml`.
- Exchange/queues/bindings для `corvex.mail` и `mail.inbound.received` не задекларированы.
- SMTP читает DATA через `readAllBytes()` до проверки лимита: большое письмо сначала целиком попадёт в heap. Нужен потоковый лимит на уровне SubEtha/storage.
- Нет submission listener с AUTH, STARTTLS/implicit TLS, исходящей очереди, retry/DSN, SPF/DKIM/DMARC и полноценной политики relay.
- Mail-storage не имеет публичного/internal API, MIME-разбора, доставки по получателям, квот и индексации.

**Gate:** `CORVEX_SMTP_ENABLED=false`, MX не публиковать до сквозного теста «письмо принято один раз, пережило рестарт, попало в Maildir и индекс».

#### P0-03. IMAP/POP3 отсутствуют как работающие протоколы

- IMAP задан интерфейсом `ImapServerPort`, но адаптера Apache James и listener bean нет.
- POP3 содержит только Spring Boot application class.
- Порты Compose опубликованы, однако за ними нет протокольной машины.

**Gate:** Stage 3 на Apache James/SubEtha/GreenMail, тесты Thunderbird/Outlook, TLS, app-passwords и лимиты аутентификации. Собственные RFC-парсеры не писать.

#### P0-04. Чат Stage 4 не является доверенной системой сообщений

- Сообщения не сохраняются, ID создаётся случайно, идемпотентность не реализована.
- Членство в комнате, `CHAT_WRITE`, read-only каналы и право подписки на topic не проверяются.
- В chat-service нет полноценного STOMP authentication interceptor/SecurityFilterChain; JWT из CONNECT не превращается в надёжный Principal.
- RabbitMQ STOMP credentials берутся из окружения с небезопасным standalone fallback.
- Chat-file-service не имеет upload/download, AV-статусов и проверки прав.

**Gate:** не подключать реальный чат к корпоративным данным до persistence + authorization на CONNECT/SUBSCRIBE/SEND и тестов изоляции комнат.

#### P0-05. JaCoCo 70% почти наверняка заблокирует `mvn verify`

Во всех сервисах стоит LINE COVEREDRATIO `0.70`, но большинство модулей имеет один smoke-тест с проверкой длины строки. Это хороший целевой порог, но текущий `verify` следует ожидать красным даже при успешной компиляции.

**Решение:** не снижать порог молча. Нужны unit/Testcontainers тесты auth/admin, контрактные тесты gateway и честный временный CI на `test` с отдельным планом покрытия.

### P1 — высокий приоритет перед расширением пилота

#### P1-01. Spring Boot 3.2.5 вне открытой поддержки

Spring официально отметил 3.2.12 как конец open-source support для ветки 3.2.x. Используемая 3.2.5 старше финального патча и тянет старые Tomcat/Jackson/Hibernate и Spring Cloud 2023.0.1.

**План:** отдельный апгрейд на поддерживаемую ветку, совместимую с Java 17, с полным `mvn test`, проверкой Spring Cloud Gateway, Security и STOMP relay. Не совмещать апгрейд с Stage 2 в одном изменении.

#### P1-02. Отзыв access JWT действует не мгновенно

Logout, блокировка, смена пароля и изменение прав отзывают refresh-сессии, но уже выпущенный access token живёт до 15 минут. Redis blacklist по `jti` пишется при logout, однако gateway/resource servers его пока не читают.

**План:** Stage 5 hardening — проверка blacklist/version claim либо сокращение TTL для чувствительных операций с осознанной ценой нагрузки.

#### P1-03. TOTP и пароли приложений: replay и стоимость проверки

- Сервер не хранит последний принятый TOTP counter; перехваченный код теоретически можно повторно использовать внутри окна допуска при новой сессии/операции.
- Количество app-passwords на пользователя не ограничено.
- `verify-password` последовательно выполняет Argon2id `matches` по всем app-passwords. Протокольный слой Stage 3 обязан добавить rate limit, lockout и лимит количества паролей; иначе IMAP/SMTP AUTH станет дорогой мишенью.

#### P1-04. Эфемерные fallback для криптографии опасны при ручном запуске

- Если JWT private key не найден, auth-service генерирует эфемерную пару и продолжает работу с warning.
- Если `CORVEX_TOTP_ENC_KEY` не задан, используется эфемерный AES-ключ: после рестарта сохранённые TOTP-секреты станут нерасшифруемыми.
- В standalone `application.yml` нескольких сервисов остались `change-me` пароли инфраструктуры. Compose для основных секретов требует значения, но ручной запуск вне Compose может создать ложное ощущение рабочей конфигурации.

**План:** для production-профиля сделать отсутствие JWT/TOTP ключей startup-fatal. Эфемерный режим оставить только явному dev-профилю.

#### P1-05. Internal token — общий секрет, а не конечная модель доверия

Текущий токен существенно лучше одной сетевой изоляции, но:

- один секрет разделяют auth-service и admin-service;
- трафик внутри Docker-сети идёт по HTTP;
- ротация требует синхронного рестарта обоих сервисов;
- notification webhook Alertmanager по-прежнему полагается только на внутреннюю сеть.

**План:** Stage 5 — отдельные credentials per caller или mTLS, секрет из Docker secrets/файла, ротация без простоя и подпись/токен для Alertmanager webhook.

#### P1-06. Actuator внутри сервисной сети шире необходимого

Все сервисы публикуют `health,info,prometheus,metrics`, gateway дополнительно `gateway`. Наружу через маршруты это не выставлено, но любой скомпрометированный контейнер в app/data сети получит операционную телеметрию и карту маршрутов.

**План:** отдельный management port/network или аутентификация Actuator, минимально необходимый набор endpoint для Prometheus и admin health.

#### P1-07. Аудит административных действий — best effort

`AuditService.record` перехватывает ошибки записи и только логирует их, чтобы не ронять основное действие. Для расследования инцидентов это означает возможную потерю именно той записи, которая нужна.

**План:** transactional outbox или обязательная запись аудита в одной локальной транзакции там, где действие локально; для cross-service операций — durable outbox и алерт на сбой аудита.

#### P1-08. Нет строгого CSP

Edge nginx ставит HSTS, `nosniff`, frame и referrer policy, но не CSP. Причина техническая: Vite legacy plugin вставляет inline bootstrap-скрипты, поэтому `script-src 'self'` без hash сломает Chrome 109 fallback.

**План:** генерировать hash/nonce в сборке либо выносить legacy bootstrap во внешние файлы; сначала Report-Only на пилоте, затем enforcing.

#### P1-09. Демо и будущие модули всё ещё содержат неактивные контролы

В demo mail/chat часть кнопок визуально присутствует, но не подключена: скачивание вложения, «ещё», новый разговор, вложение и голосовое сообщение в чате. Это не дефект Stage 1 API, но UX-долг: пользователь не должен догадываться, где продукт, а где макет.

**План:** на Stage 2/4 либо подключить действия, либо явно отключать с понятной подсказкой этапа. Текущие баннеры демо и этапов снижают риск, но не устраняют его полностью.

#### P1-10. React Router: две moderate уязвимости и отложенный major upgrade

`npm audit` сообщает open redirect через backslash и constructor injection в SSR hydration. В Corvex:

- SSR не используется;
- все `Link`, `Navigate` и `useNavigate` цели захардкожены внутренними путями;
- пользовательский `returnTo` не принимается.

Поэтому риск временно принят. Принудительный переход на React Router 7 в этом проходе не делался: нужно отдельно проверить Chrome 109/legacy bundle и все маршруты. Если появится redirect из пользовательских данных, приоритет сразу станет P0.

### P2 — качество, эксплуатация и развитие

- **Нет CI в репозитории.** GitHub App текущей сессии не позволила опубликовать `.github/workflows/*` без разрешения `workflows`. Скрипт скриншотов уже есть; владельцу репозитория нужно добавить workflow с frontend, Maven matrix и Playwright.
- **Нет component/E2E тестов.** Текущие 12 фронтенд-тестов закрывают i18n, Unicode и refresh single-flight, но не клики, формы и маршруты.
- **Login attempts и refresh sessions растут бесконечно.** Нужны retention jobs и индексы под очистку.
- **Lockout только по username.** Это защищает пароль, но позволяет распределённо блокировать жертву; нужна комбинация username/IP/risk policy и разблокировка администратором.
- **Настройки пока не имеют всех потребителей.** `server_settings` валидируются и аудируются, но Stage 2/4 сервисы должны реально читать лимиты, квоты, POP3 и `requireTotp`; парольная длина в auth пока зафиксирована политикой Stage 1.
- **Health dashboard показывает свободное место корня контейнера**, а не тома почты; Rabbit queue depth суммирует все очереди. Для эксплуатации нужны отдельные метрики Maildir, PostgreSQL, Elasticsearch и очередей по именам.
- **Cross-service create user не атомарен.** Компенсация disable при сбое групп есть, но сбой после назначения групп и до аудита может дать активную учётку при ответе 500. Нужен outbox/idempotency key.
- **OpenAPI mail/chat описывает целевые контракты**, а не текущую реализацию. README и READINESS обязаны продолжать явно разделять Stage 1 и будущие этапы.
- **Bundle дублируется modern+legacy.** Это цена Chrome 109. Следует следить за размером ChatPage из-за Markdown/DOMPurify и не подключать тяжёлые emoji-картинки.
- **Голосовые/hover-only действия чата** должны получить `focus-within` доступность и мобильный сценарий на Stage 4.

## 6. Оценка фронтенда

Сильные стороны после аудита:

- Quiet Work сохраняет спокойную светлую иерархию и не возвращает emoji-иконки/тёмную тяжёлую оболочку.
- RU/EN покрывают shell, вход, почту, чат, админку, безопасность, смену пароля, demo-данные и ошибки API.
- Session flow не хранит refresh token в JS; access token живёт в памяти, refresh — HttpOnly cookie.
- Lazy routes отделяют админку и чат от первого экрана; legacy bundle сохранён ради Chrome 109.
- Emoji остаются текстом, а не внешней картинкой; Unicode-обрезка не ломает сложные последовательности.

Остаточные UX/технические долги:

- Скриншоты сняты и просмотрены, но автоматической визуальной регрессии в CI пока нет: кадры нужно переснимать при изменениях UI тем же скриптом и сравнивать вручную или pixel-diff инструментом.
- Нет проверки реального Windows 7 и Chrome 109: portable Chromium 153 подтверждает современный рендер и production bundle, но не заменяет legacy-стенд. Системный emoji-шрифт Windows 7 может рисовать базовые emoji монохромно, а сложные пользовательские последовательности — составными глифами; в минимальной Linux-среде без Noto Color Emoji видны tofu.
- Demo mail/chat нельзя смешивать с боевыми обещаниями. В UI это обозначено баннерами, но часть контролов всё ещё декоративна.
- Markdown разрешает ссылки; нужны политика внешних ссылок, `rel`, подтверждение ухода и серверная санитизация на Stage 4.
- Нет автоматической проверки контраста и полного клавиатурного сценария.

## 8. Итоговое заключение

Аудит не обнаружил причин переписывать Stage 1. Архитектурные границы в целом здоровые: auth владеет учётками, admin владеет RBAC, gateway не принимает бизнес-решений, сервисы не ходят в чужие базы, а почтовые протоколы изначально отделены портами под зрелые библиотеки.

Главный риск проекта сейчас не отдельная строка кода, а **разрыв между статически аккуратной реализацией и отсутствием runtime-доказательств**. Следующий инженерный шаг должен быть не новой функцией, а воспроизводимым Gate A: собрать, запустить, пройти сценарий, восстановить из бэкапа и зафиксировать результат. После этого Stage 2 можно делать на уже укреплённом Stage 1 без риска потерять первую настоящую почту.
