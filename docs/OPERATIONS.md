# Эксплуатация

Как обслуживать работающий Corvex: смотреть состояние, делать и проверять резервные
копии, получать алерты, обновляться и откатываться, разбирать сбои и переносить стенд на
сервер. Установка — [`INSTALL.md`](INSTALL.md); проверки — [`TESTING.md`](TESTING.md).

## 1. Ежедневные команды

```bash
docker compose ps                          # состояние и health
docker compose logs -f --tail 100          # все логи (или Loki в Grafana)
docker compose logs --tail 200 <сервис>    # один сервис, искать Caused by
docker compose restart <сервис>            # перезапуск
docker compose up -d --build <сервис>      # пересборка одного сервиса
docker compose down                        # остановка, данные в томах сохраняются
```

`docker compose down -v` удаляет тома. Это допустимо **только на пустом стенде без
данных**.

## 2. Наблюдаемость

Мониторинг включается профилем: `docker compose --profile monitoring up -d`.

| Компонент | Что даёт |
|---|---|
| Prometheus | метрики `/actuator/prometheus` всех сервисов, правила алертов, хранение 30 дней |
| Alertmanager | группировка, подавление, silence, рассылка |
| `alert-relay` | независимые внешние каналы: SMTP, Telegram, MAX |
| Grafana | дашборды, доступ по адресу `/grafana/` с allowlist-подсетью |
| Loki + Promtail | структурированные JSON-логи с `requestId` из gateway |

На что смотреть в первую очередь:

- очереди RabbitMQ и DLQ: рост DLQ означает «ядовитые» сообщения, а не медленную работу.
  Исключение — недоступность `mail-storage-service`: тогда письмо возвращается в очередь
  (`ImmediateRequeue`), а не уходит в DLQ;
- заполнение тома с данными: алерт при 80 %, решение о диске принимается до отказа;
- память контейнеров: `docker stats` и `scripts/runtime_usage.py`; OOM-killer в событиях
  означает нехватку RAM, а не «медленный сервер»;
- задержка поиска и состояние Elasticsearch `yellow`/`red`;
- bounce-rate и DSN при внешней отправке.

**72 часа наблюдения** — обязательный этап перед пилотной группой: очереди, DLQ, диск,
память, bounce-rate, отсутствие restart loop. Результат фиксируется отчётом с датой и SHA.

## 3. Резервные копии

```powershell
.\scripts\backup.ps1 -BackupRoot D:\CorvexBackup
```

Что попадает в копию:

| Данные | Формат |
|---|---|
| 4 базы PostgreSQL | binary-safe дампы |
| Maildir, вложения CAS, файлы чата и диска | архивы томов |
| `.env`, сертификаты, ключ JWT | файлы |
| Манифест | `manifest.json` с SHA-256 каждого файла |

Индекс Elasticsearch не входит — он перестраивается из баз. Очереди, сессии и метрики
тоже не входят.

Правила:

1. **Другой физический носитель.** Копия на том же диске не защищает ни от отказа, ни от
   шифровальщика.
2. Минимум 2 копии, лучше 3 — история на месяц. Копии не дедуплицируются, поэтому объём
   считается как данные × число копий.
3. Расписание — Планировщик Windows, например ежедневно в 02:30:
   `powershell -ExecutionPolicy Bypass -File C:\Corvex\scripts\backup.ps1 -BackupRoot D:\CorvexBackup`.
4. **Восстановление проверяется.** Копия без проверенного восстановления — это надежда.

### Проверка восстановления без риска для рабочего стенда

```powershell
# -BackupDir обязателен у обоих скриптов; без него они падают на параметре.
.\scripts\restore.ps1 -BackupDir D:\CorvexBackup\<timestamp> `
  -ProjectName corvex-restore-drill -DataOnly -Force
.\scripts\restore_verify.ps1 -BackupDir D:\CorvexBackup\<timestamp> `
  -ProjectName corvex-restore-drill
```

Скрипты поднимают данные в отдельном проекте на других портах: 4 базы и 3 файловых тома
сравниваются с копией, рабочие тома и порты не затрагиваются. Команды и границы проверки —
[`../scripts/README.md`](../scripts/README.md).

Раз в квартал — полное учебное восстановление на отдельной машине с контрольными ящиками,
вложениями, событием календаря и комнатой чата. Целевое время — не более 4 часов.

## 4. Алерты

Два независимых пути:

1. **Внутренний:** Alertmanager → `notification-service` → RabbitMQ → почта Corvex. Быстро
   и ничего не требует, но **не спасёт при отказе самой почты**.
2. **Внешний:** Alertmanager → `alert-relay` → SMTP независимого провайдера, Telegram или
   MAX. Не использует RabbitMQ и почту Corvex.

Настройка — `/admin/settings` → «Алерты и доставка», только `SUPER_ADMIN`. Секреты
write-only и хранятся в AES-256-GCM. Env-переменные остаются fallback.

### Частота

`CORVEX_ALERT_REPEAT_INTERVAL` (по умолчанию 4h) и
`CORVEX_ALERT_CRITICAL_REPEAT_INTERVAL` (30m); в UI — числом минут, допустимы 15m, 1h, 6h,
1d. Alertmanager отправляет минутный delivery tick, но это не письмо каждую минуту:
`notification-service` и `alert-relay` подавляют повторы по эффективной политике отдельно
для каждого канала. При частичной ошибке повторяется только неудачный канал.

### Внешний SMTP

Незашифрованный SMTP не поддерживается: только `starttls` (обычно 587) или `ssl` (465).
Username можно оставить пустым, если провайдер разрешает relay без логина.

### Telegram

Нужен свой бот из BotFather и **числовой** ID получателя: `123456789` для личного чата или
`-100...` для группы. `@username` не принимается. Порядок: вставить token → нажать Start в
чате с ботом (или добавить в группу и отправить `/start`) → «Найти чаты» → явно выбрать
получателя → включить канал. Пустой список найденных чатов не является успешным
подключением. Relay использует исходящий `getUpdates`: публичный webhook и порт не нужны,
не настраивайте для того же token второй consumer.

Внешний SMTP/Telegram/MAX получают только те алерты, которые вы включили в категориях.
Проверка канала — `scripts/alert_e2e.py` (создаёт один синтетический алерт и завершает его);
не останавливайте рабочий сервис ради проверки.

### Silence

```powershell
.\scripts\alerts.ps1 silence -Minutes 60
.\scripts\alerts.ps1 silence -Minutes 120 -Service chat-service:8088
.\scripts\alerts.ps1 status
.\scripts\alerts.ps1 unsilence -SilenceId <uuid>
```

Silence отключает новые уведомления обоих каналов, но не останавливает мониторинг и не
скрывает сбой. Максимум — 30 суток. Уже отправленные сообщения не отзываются.

## 5. Обновление и откат

```powershell
git pull
docker compose up -d --build
docker compose ps
```

Миграции Flyway применяются при старте и только аддитивны (expand-contract), поэтому откат
образа не требует отката схемы.

Порядок безопасного обновления:

1. Резервная копия (`backup.ps1`) и запись текущего SHA.
2. Обновление и сборка.
3. `docker compose ps` — все сервисы `healthy`/`Up`.
4. Дымовые проверки из [`INSTALL.md`](INSTALL.md) §9.
5. Почтовые протоколы включаются последними и по одному.

Откат: вернуть предыдущий коммит или теги образов и повторить `up -d`. Проверьте, что
предыдущая версия совместима с уже применёнными миграциями: аддитивные миграции это
позволяют, но удаление колонок в будущем потребует отдельного плана.

Перед каждым изменением `.env` сохраняйте копию файла с датой: откат `.env` — тоже откат.

## 6. Диагностика

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| Maven не компилирует сервис | несовпадение API зависимости или ошибка типов | собрать один сервис без тестов, исправить **первую** ошибку, не понижать версии «на всякий случай» |
| Тесты проходят, падает JaCoCo `verify` | покрытие ниже порога 70 % | добавить тесты на критичную логику; порог менять только осознанным решением |
| Spring-контекст не стартует | дублирующийся или отсутствующий bean, неверный env, недоступны PostgreSQL/Redis/RabbitMQ/Elasticsearch | читать полный cause-chain в `docker compose logs --tail 200` |
| Flyway или JPA `validate` падает | схема расходится с entity | добавить **новую** миграцию, применённую не редактировать |
| `401`/`503` на internal API | разные или пустые `CORVEX_INTERNAL_API_TOKEN`, потерян JWT-ключ, недоступен JWKS, разошлось время | сверить секрет во всех сервисах, persistent PEM-ключ, NTP |
| SMTP отвечает `451`, письмо не появляется | недоступны storage/RabbitMQ, нет прав на spool, превышена квота | логи SMTP/storage, очереди и DLQ; не удалять spool вручную, пока не найден `rawRef` |
| Письмо продублировалось или потерялось после рестарта | at-least-once AMQP и отсутствие полного transactional outbox | воспроизвести остановку в каждой точке конвейера, добавить идемпотентность и регрессионный тест |
| После рестарта `mail-storage-service` письма лежат в `mail.spam.inbound.dlq` | рестарт был дольше окна ретраев (до 2026-11 сообщения уходили в DLQ за ~15 секунд) | обновить spam/AV-сервисы: транспортный сбой теперь возвращает сообщение в очередь, окно ретраев ≈ 50 с; уже попавшие в DLQ письма повторно не публикуются автоматически — их перечитывает повторный проход импорта внешнего ящика (записи в статусе `QUEUED` не считаются доставленными) |
| Нужно убедиться, что рестарт больше не теряет письма | — | `scripts/verify-dlq-resilience.ps1` (Windows) или `scripts/verify-dlq-resilience.sh` (Ubuntu-VM): снимает счётчики очередей, перезапускает сервис, ждёт `healthy`, ждёт опустошения очередей и выносит вердикт по росту DLQ. Очереди не чистит |
| Webmail `403/422/413` при отправке | нет права, отправитель не `ACTIVE`, домен не принят, письмо больше лимита | проверить группы, статус, домены и размер MIME; права менять в админке, а не в коде |
| Submission не принимает AUTH/STARTTLS | нет сертификата, ключ не PKCS#8 PEM, порт 587 закрыт, включён TOTP и используется основной пароль | проверить `fullchain.pem`/`privkey.pem`, app-password, envelope sender |
| Внешняя почта в спаме или bounce | нет PTR, SPF не покрывает отправителя, DKIM не совпадает, закрыт исходящий 25 | смотреть DSN, начать с SPF `~all` и DMARC `p=none`, настроить PTR, mail-tester ≥ 9/10 |
| После пересборки сервиса сайт отдаёт `502` | nginx резолвил имена при старте | `docker compose restart nginx`; исправление конфигурации с `resolver` — отдельная проверка |
| Напоминание календаря не приходит | разный `CORVEX_INTERNAL_API_TOKEN`, неверный `CORVEX_CALENDAR_FROM`, ошибка SMTP | логи `notification-service` и `mail-storage-service`; `503` означает, что планировщик повторит |
| На телефоне чат «другой»: история есть, новые сообщения не приходят | телефон открывает стенд по LAN-адресу — это другой origin, и `chat-service` отклоняет WebSocket (403 на `/ws/chat/info`); плюс `CORVEX_AUTH_COOKIE_SECURE=true` не даёт сохранить cookie по http | `scripts/diagnose-mobile-access.ps1`: покажет разрешённые origin и живую проверку; добавить `http://<LAN-IP>:8080` в `CORVEX_WEB_ORIGINS` через запятую, `docker compose up -d --force-recreate chat-service web-gateway` |
| На Windows 7 интерфейс отличается от скриншотов | отдан modern-бандл вместо legacy, кэш | проверить, что каталог `assets` содержит `*-legacy-*.js`, и очистить кэш |
| Elasticsearch перезапускается | мало RAM или низкий `vm.max_map_count` | ≥2,5 ГБ только ему; `sysctl -w vm.max_map_count=262144` |

Общий принцип: сначала фиксируйте факты (SHA, версии, первая ошибка, `docker compose ps`,
хвост логов), потом меняйте что-то одно. Не «лечите» сбой массовым обновлением или
отключением проверки.

## 7. Перенос на сервер

Порядок работ, при котором каждый день заканчивается проверенным результатом. Пятница —
резерв на сбой, а не на новые функции.

| День | Результат дня |
|---|---|
| 1 | полный `mvn -B clean verify` на точном SHA; чистая установка на пустых томах; все контейнеры `healthy`; SHA записан |
| 2 | домен, DNS, TLS, вход, админка, здоровье API |
| 3 | внешняя почта: приём 25, отправка, PTR, DKIM/SPF/DMARC, mail-tester |
| 4 | клиенты, чат, календарь и напоминание, алерты на внешний ящик |
| 5 | backup → restore на отдельном стенде, откат, старт 72 часов наблюдения |
| выходные | исправления и повторный полный прогон, без новых функций |

Что можно сделать, пока домена нет: поставить инструменты, прогнать полный reactor, поднять
стек на пустых томах, посчитать размер (`scripts/capacity.py`), снять фактическое
потребление RAM (`scripts/runtime_usage.py`), выполнить `scripts/preflight-server.ps1`
(версии, диск, память, порты, `.env`, одинаковость внутреннего токена, `compose config`,
часы), потренировать восстановление. Домен нужен только для TLS, MX и внешней доставки.

Порядок включения, чтобы не сделать сервер недоступным: сначала веб (443/80), затем SMTP
25/587, затем IMAP/POP3 — по одному, с проверкой после каждого. Публичные порты баз
(`5432`, `5672`, `6379`, `9200`) не открываются никогда.

## 8. Что остаётся открытым

- **Внешние ящики Google в статусе Testing разваливаются на восьмой день.** Пока
  приложение не переведено в Production, Google выдаёт refresh token на 7 дней. После
  этого сбор писем останавливается, в интерфейсе появляется `reauthRequired`, в логах —
  `invalid_grant`. Это не дефект Corvex и не «сломался сбор»: токен истёк по политике
  провайдера. Что делать при появлении `reauthRequired`:
  1. не удалять внешний ящик и не менять его настройки — учётные данные не потеряны;
  2. пройти вход в Google заново через мастер (кнопка повторной авторизации);
  3. на пилоте это ожидаемое событие: его планируют, а не расследуют;
  4. для постоянной работы нужен статус Production, а для restricted-scope
     `https://mail.google.com/` он требует верификации приложения — см.
     [`MIGRATION.md`](MIGRATION.md) §6.
  Держите это в голове при выборе даты пилота: если он длиннее недели, вход придётся
  повторить.
- 72 часа наблюдения закрываются только на следующей неделе.
- Полная матрица IMAP/POP3 в Thunderbird и Outlook; Outlook не проверялся.
- Нагрузка до 1000 сотрудников, security-проход, согласованная платформа G4.
- Общие календари, AD/LDAP, второй компьютер.

Текущее состояние доказательств — [`STATUS.md`](STATUS.md); планы — [`ROADMAP.md`](ROADMAP.md).
