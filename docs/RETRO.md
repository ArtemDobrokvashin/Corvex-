## 2. Что реально закрыто

- **P2 — впервые за проект полный `mvn verify` по всему reactor.** Не «модуль зелёный»,
  а 14 проектов до конца, run `44266849755`, повтор `44267475424`.
- **P4 — чистая установка с нуля.** `C:\corvex-clean`, 20 контейнеров `healthy`, миграции с
  пустых БД, вход администратором, письмо внутри домена, сквозной алерт `PASS=5`.
- **P1 — доказан живьём.** Вход через Google, самостоятельное обновление refresh-токена,
  отзыв согласия → `409` с текстом → повторный вход → сбор снова работает (`fetched_count =
  200`). Это лежало в `STATUS.md` с 19.11, а в таблице приёмок стояло «почти» — см. минус №3.
- **DLQ при рестарте** — найден настоящий корень: keep-alive соединение, закрытое бэкендом,
  и ретраи 1+2+4+8 ≈ 15 с против ~25 с перезапуска. Не «увеличили таймаут», а разобрали
  механику.
- **IMAP перестал врать про пароль.** Раньше любой ответ auth-service, кроме `200`,
  превращался в «неверный пароль». Теперь `mail-imap-service` пишет код и причину, при
  старте делает самопроверку, а `login_probe.py` печатает `SUCCESS` до того, как вы начнёте
  сомневаться в собственной памяти.

## 3. Плюсы: что мы делали хорошо

1. **Доказательство вместо галочки.** У каждой закрытой приёмки есть run id, SHA, команда
   и колонка «чего это не доказывает». Это редкая дисциплина, и она работала: именно она
   поймала, что P4 «пройден» только после пятого прогона алерта, а не после первого
   зелёного лога.
2. **Корень, а не симптом.** Три раза подряд вместо «подкрутить таймаут» мы доходили до
   первоисточника: семантика `INVALID_LOGIN` в James 3.8.2, механика keep-alive в DLQ,
   усечение многострочного аргумента при передаче в `docker`. Это дороже по времени и
   дешевле по последствиям.
3. **Каждый ложный зелёный стал стражем.** После каждого обмана появилась проверка:
   `restore_verify` требует маркер `<db>_logical_match`; `alert_e2e` проверяет вход **до**
   создания алерта; `docs_audit` сверяет маршруты, ссылки, миграции и `.env`; CI гоняет три
   задания на каждый PR. Список обманов больше не растёт — он превращается в тесты.
4. **Стоп-лист выдержан.** С 18.11, когда приёмка стала правилом, ни одной новой функции:
   только приёмка, диагностика, документация и CI. Соблазн был (очередь идей длинная), но
   разрыв «написано / проверено» не вырос.
5. **Твои поправки экономили часы, а не минуты.** «А какое письмо ты ищешь?» — до того как
   чинить. «Проверим, что пароль подошёл, и выведем success» — превратило гадание в
   проверку. «Мы ж пароль не вводили в PowerShell» — убрало ложный путь с переменной
   окружения. «Чет не туда копаем, погугли» — привело к исходникам James. Четыре реплики,
   каждая сэкономила как минимум один цикл сборки.
6. **Документация стала проверяемой машиной**, а не обещанием: `docs_audit` — 0 ошибок,
   0 предупреждений; команды в документации сверяются с `param(...)`; схема БД сверяется с
   JPA-сущностями. Это уже не «мы старались», а тест.

## 4. Минусы: что шло плохо

1. **Один диагноз стоил девять PR.** Цепочка IMAP — #184, #185, #186, #187, #188, #189,
   #191, #192, #193. Каждый PR по отдельности правильный, вместе — девять сборок,
   перезапусков и ожиданий. Причина: я чинил по гипотезе на каждом шаге вместо того, чтобы
   сразу собрать полную диагностику (что в итоге и сделал в #193). **Лечим:** правило
   «один диагноз — один прогон», скрипт печатает версию, код ответа, причину и хвост лога.
2. **Ложный зелёный от нашего же скрипта.** `restore_verify.ps1` напечатал
   `Restore verification OK: 4 databases and 4 file volumes match the backup`, не сверив ни
   одной базы, и я сначала принял это за успех. Худший класс ошибки: не «сломалось», а
   «врёт, что работает». **Лечим:** успех только по маркеру и только с числом проверенных
   объектов.
3. **Статус противоречил собственному доказательству.** В таблице приёмок P1 стоял «почти:
   отзыв согласия не прогонялся», а в `STATUS.md` тот же отзыв расписан по минутам с `409` и
   восстановлением сбора. Причина: писал статус по памяти сессии, а не открыв документ.
   **Лечим:** перед изменением статуса открывается строка-доказательство; в этом PR
   противоречие исправлено.
4. **План с несуществующим параметром.** `-ProjectName` у `verify-dlq-resilience.ps1`,
   которого нет в `param(...)`. Поймал тест `test_doc_commands`, но написал его я — и в
   понедельник ты бы ловил ошибку параметра вместо проверки. **Лечим:** план проходит те же
   проверки, что и документация (уже проходит, поэтому и поймали).
5. **Три источника правды разъехались.** `STATUS.md` (585 строк нарратива), `ACCEPTANCE.md`
   (таблица статусов) и `PLAN-MONDAY.md` (план) уже говорят разное: «3 тома» против «4 тома»,
   P1 «почти» против «доказано», P3 «OK» против «недействительно». **Лечим:** `STATUS` —
   только доказательства, `ACCEPTANCE` — только статус, `PLAN` — только действия; вместо
   копий — ссылки. Расхождения из этого списка исправлены этим PR.
6. **Долгие паузы и потеря нити.** Ты уходишь, перезагружаешь компьютер, возвращаешься
   через часы; каждый мой шаг ждал вывода. Часть времени ушла на восстановление контекста, а
   не на работу. **Лечим:** карта «этап / статус» перед каждым действием, блоки по 15–20
   минут, один блок — один заход.
7. **Проверки жили отдельно от CI.** Все скрипты приёмки (`backup`, `restore`, `alert_e2e`,
   `verify-dlq`) требуют Docker и живого стенда, поэтому в CI их нет. Отсюда поздние
   находки: четыре дефекта `restore_verify` всплыли в самом конце недели. **Лечим:** у
   каждого скрипта — прогон с подставным `docker` и тест на текст успеха; живой прогон
   остаётся за тобой.
8. **Секрет оказался в переписке.** Пароль пришёл в чат, хотя правило «секреты не
   присылать» было. Отчасти моя вина: я сформулировал так, что проще было прислать, чем
   ввести локально. **Лечим:** только скрытый ввод через `getpass`, в инструкциях — «введите
   у себя», а не «пришлите мне».

## 6. Что меняем со следующей недели

Пять правил, они же — §1 плана недели:

1. **Один диагноз — один прогон.** Не прошу второй вывод, пока не исчерпал первый.
2. **Успех = маркер + число.** Нет числа проверенных объектов — нет успеха.
3. **Один источник правды.** `STATUS` — доказательства, `ACCEPTANCE` — статус, `PLAN` —
   действия. Копий не пишем, ставим ссылки.
4. **Перед статусом — открыть доказательство.** Любая строка «пройдено» пишется с
   документом перед глазами, а не по памяти.
5. **Батчинг для тебя.** Один блок команд на день, сначала только чтение, весь вывод одним
   куском; секреты — только скрытым вводом.

## 7. Чего эта оценка не доказывает

Оценка субъективна: это разбор процесса, а не измерение качества продукта. Цифры PR и
строк точны, но «плюсы» и «минусы» — интерпретация, и с частью из них можно спорить.
Оценка не учитывает дни до 16.11: там было 132 смерженных PR, и сравнивать недели по объёму
бессмысленно — 16–20.11 это неделя приёмки, а не разработки.
