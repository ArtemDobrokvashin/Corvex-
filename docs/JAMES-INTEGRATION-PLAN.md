# Apache James: границы интеграции с Corvex

Статус: исследование и проект, не внедрено. `experiments/james-lab` не подключён
к Corvex и ещё не запускался с настоящим James. Не устанавливать на рабочий
сервер и не импортировать реальные письма до прохождения приёмки.

## Текущее разделение ответственности

* `mail-imap-service` использует протоколы James 3.8.2, но `CorvexMailboxManager`
  и `CorvexMessageManager` обращаются через `ImapStorageClient` к собственному
  `mail-storage-service`. POP3 аналогично обращается к `ProtocolStorageClient`.
  Поэтому наличие James в зависимостях **не означает**, что James управляет
  текущим хранилищем и его транзакциями.
* SMTP использует SubEtha; доставка `MailDeliveryService.deliver` принимает
  результат конвейера и пишет файл/метаданные. В `MailSendService` также есть
  создание исходящего MIME, проверка разрешений и разветвление на локальную,
  внешнюю и Sent-доставку. Подмена только одной ветви может обойти AV/спам,
  квоты, идемпотентность или дублировать отправку.
* Публичный `MailController` берёт владельца из JWT subject и проверяет
  разрешения. DTO используют UUID писем и папок, UID папки и курсоры; текущий
  фронтенд зависит от них. `InternalProtocolController` — отдельный внутренний
  API, не следует предоставлять его как пользовательский.
* `ImapAuthClient` вызывает auth-service по внутреннему токену и проверяет статус
  пользователя; там есть основной пароль и app-password. Текущий код обрабатывает
  не-200 ответы некоторых вызовов как отсутствие результата; отдельно проверить
  различение отказа в доступе и временной ошибки сервиса. Это наблюдение о коде,
  не вывод о поведении James.

## Принципы выбора реализации

1. **Один источник истины для ящиков и MIME.** James должен владеть операциями
   над своими данными; прямую запись Corvex в файлы/таблицы James запрещаем.
   Индекс или кэш Corvex не должен быть вторым авторитетным хранилищем писем.
2. **Идентификация и доступ.** UUID владельца берём из проверенного JWT, права
   проверяем на сервере. Не передавать чужой mailbox ID без проверки владельца;
   не сохранять пользовательские пароли для серверного webmail. Нужен изученный
   и проверенный способ доверенного доступа/делегирования в конкретной сборке
   James с минимальными правами, аудитом и отзывом — наличие такого механизма
   ещё не подтверждено. Не использовать demo-учётные записи в интеграции.
3. **Нет двойной доставки.** На первом этапе выбрать один маршрут приёма/отправки
   на изолированном стенде. До проектирования интеграции нельзя просто подключить
   James к существующей очереди или одновременно включить два SMTP listener.
4. **Ошибки не скрывать.** Неизвестный результат сетевой операции не считать
   ни гарантированным отказом, ни успехом. Для повторной доставки нужен
   согласованный механизм идемпотентности; IMAP APPEND сам по себе не доказанная
   операция exactly-once. Отключение auth, AV или James должно обрабатываться
   безопасно и проверяться отдельно.
5. **Не переносить соответствие UUID ↔ UID на доверии.** UID уникален в пределах
   папки и UIDVALIDITY; MOVE может изменить UID. Постоянный ID сообщения и его
   связь с James должны быть определены и протестированы для каждого пути. Не
   обещать сохранение старых UID при импорте: исследовать возможность и при
   необходимости спланировать синхронизацию IMAP-клиентов заново.

## Контракты, которые необходимо воспроизвести

| Область | Текущий контракт / риск перехода | Проверка для приёмки |
|---|---|---|
| Ящики | JWT owner UUID; имена, вложенность, system folders; права создания; web удаляет только пустую | Два пользователя, вложенные и системные папки, гонки, запрет чужого доступа и удаления непустой папки |
| Список и чтение | UUID/UID, курсор, flags, реальный получатель, MIME, вложения, CID | Списки и чтение через web и IMAP, побайтное сравнение оригиналов, owner isolation, пагинация при изменениях |
| Операции | FLAGS, MOVE, COPY, EXPUNGE, POP3 DELE/QUIT; UID и MODSEQ | Одновременные изменения и перезапуск, предсказуемая обработка неизвестного результата; нет потерянных писем |
| Приём | SMTP → spool → спам/AV → доставка; `rawRef` + owner для дедупликации | Повтор событий, сбой AV/спам/очереди, отсутствие обходного маршрута и ложного CLEAN |
| Отправка | Проверки внутренних/внешних/массовых прав, внешние аккаунты, Sent, BCC | Ограничения прав, повтор при таймауте, владельцы внешних ящиков, идентичность MIME и отсутствие утечки BCC |
| Протоколы | IMAP/POP3, TLS, app-password и отзыв, 2FA, статусы пользователей | Два клиента и два пользователя, неверный пароль, блокировка и отзыв, auth outage; никаких demo credentials |
| Обновления | Изменения должны отображаться в webmail без F5 | События из web и IMAP, потеря/повтор событий, восстановление после переподключения |
| Эксплуатация | квоты, search, monitoring, backups, очистка удалённых данных | Объём/квота, восстановление в отдельное окружение, алерты, политика удаления и хранения |

Для каждого пункта нужно отдельно зафиксировать, кто отвечает за поведение:
James, существующий Corvex-сервис или новый адаптер. Наличие соответствующего
API в James, его лицензирование, поддержка версии и семантика проверяются по
документации и исходникам именно выбранной сборки, а затем тестом.

## Контролируемый переход

1. Закрепить и протестировать версию и профиль James на отдельной сети, без
   подключения к рабочим томам и доменам. Проверить сборку, лицензии, настройки
   TLS и недоступность внутренних admin-интерфейсов извне.
2. Спроектировать идентичность и доверенный доступ webmail, после подтверждения
   интерфейсов — изолированный адаптер с контрактными тестами. Демонстрационный
   IMAP-клиент с фиксированным паролем не является этим адаптером.
3. Внедрить путь приёма/отправки с AV и политиками, протестировать idempotency,
   события, отказы и протокольные клиенты. Не включать новый путь параллельно со
   старым на одних данных.
4. Импортировать только копию данных в независимый стенд, сверить каждое письмо,
   MIME, вложения, владельца, папки и флаги; отдельно оценить UID/UIDVALIDITY,
   поиск и повтор импорта. Missing/orphans — отчёт и разбор, не очистка.
5. Провести полное восстановление backup и стресс/сбойные проверки. План
   переключения, остановки всех писателей и отката должен учитывать письма,
   принятые **после** переключения: простое возвращение старого контейнера может
   их потерять. Только после успешной приёмки — ограниченный пилот.

Решение о production-сборке не принято. Демонстрационный `demo-3.9.1` пригоден
только для начального знакомства; его учётные данные публичны, а POP3 в
upstream demo отключён. Стенд не подтверждает совместимость с Windows Server,
производительность на 1000 сотрудников или отсутствие ошибок в James.

## Результаты лаборатории и уточнение пути интеграции

На ПК изолированная demo-сборка James прошла три сводных сценария: IMAP
APPEND/COPY/флаги/MOVE/чтение MIME и базовая изоляция второго INBOX; SMTP
между двумя demo-пользователями с проверкой вложения; чтение ранее созданного
сообщения после рестартов. 3 PASS, 0 FAIL, 6 SKIP — не эксплуатационная приёмка.
Изначально после рестарта IMAP HEADER SEARCH не находил синтетическое письмо,
но прямое чтение вернуло точные байты. Лабораторная переиндексация INBOX
восстановила поиск, и после следующего обычного рестарта он работал. Причина
первого расхождения не доказана; опыт не покрывает потерю питания.

Важно: demo/JPA не подтверждает пригодность на сервер. В upstream документации
поставок JPA описывается как legacy, а документация JPA указывает, что JMAP в
этом приложении отсутствует. Рассмотреть отдельно postgres-app: его требования
к PostgreSQL, поиску, очереди и blob storage, официальный образ, версии и
возможность работы внутри единого Compose надо проверить на точном релизе;
нельзя выдавать опыт demo/JPA за тест postgres-app.

У James 3.9.1 есть код IMAP AUTHENTICATE PLAIN с авторизационной идентичностью
и делегированием, а в конфигурации описан administratorId для impersonation.
Это **направление исследования**, не готовая безопасная интеграция: неизвестно,
какая конфигурация и модель прав применимы, как связать UUID/JWT пользователя
Corvex с James и как обеспечить изоляцию, аудит и отзыв. Универсальный мастер-
аккаунт даёт широкий доступ; использовать его в работающей среде до изучения
рисков и тестов нельзя. WebAdmin также не следует выставлять наружу или считать
эквивалентом пользовательского API.

Для сравнения изучить JMAP postgres-app и ограничения проверки токена (issuer,
audience, expiry, идентичность, отзыв и отсутствие доверия к заголовкам клиента).
Не пересылать логин/пароль пользователя из webmail и не хранить их ради адаптера.
Отдельный адаптер должен на сервере проверять JWT/разрешения Corvex, и никакой
клиент не может выбирать чужой аккаунт без проверки. Ни одно решение по этой
части пока не внедрено и не прошло реальные тесты.
