# 10. Тестовая стратегия

> К пункту 10 формата вывода. Цель: критерии приёмки ТЗ §11 проверяются
> автоматически там, где это возможно; ручная проверка остаётся только для
> почтовых клиентов и парка Windows 7.

## 10.1. Пирамида

| Уровень | Инструменты | Что покрывает | Гейт в CI |
|---|---|---|---|
| Unit | JUnit 5, Mockito, AssertJ | чистая логика: TOTP (векторы RFC 6238), расчёт прав (union групп), Maildir-имена, SPAMC/INSTREAM парсинг ответов, MIME-разбор, правила сортировки, квоты | покрытие строк ≥70% на сервис (JaCoCo `check` в каждом pom) |
| Компонентные/контрактные | Spring Test + WireMock, валидация против `docs/api/*.yaml` | каждый REST-контроллер: статусы, права (403 без permission), Problem Details; контракты событий RabbitMQ схемами JSON | падение при расхождении OpenAPI и кода |
| Интеграционные | Testcontainers (PostgreSQL, Redis, RabbitMQ, ES, **GreenMail** как внешний почтовый мир, спам/clamav образы) | конвейер письма целиком: SMTP-приём → spam → AV → папка → поиск нашёл; доставка в «чужой» GreenMail; IMAP-сессии настоящим JavaMail-клиентом; миграции Flyway на чистой БД | обязательны для merge в main |
| E2E веб | Playwright (Chromium/Firefox) | сценарии: вход (+2FA), письмо туда-обратно, поиск, чат между двумя пользователями в реальном времени, смена прав группы отражается в UI, блокировка пользователя | nightly + перед релизом |
| E2E почтовые клиенты | ручной чек-лист + скриптованный JavaMail/imap-tools | Outlook 2019/365, Thunderbird115, мобильные клиенты: подключение по автоконфигу, IDLE-push, папок/флагов синхронизация, POP3 UIDL стабильность | этап 3 и каждый релиз почтового контура |
| Нагрузочные | k6 (HTTP/WS), smtp-source/JMeter (SMTP/IMAP) | см. §10.3 | перед пилотом и продом |
| Безопасность | OWASP ZAP baseline, dependency-check, ручной пентест-проход | open relay (обязательно!), XSS в HTML-письмах, IDOR на чужие письма/комнаты, brute force, протечки поиска за пределы прав | релизный гейт |

## 10.2. Критичные негативные тесты (выделены отдельно)

- **Open relay**: внешний SMTP без авторизации не может отправить письмо ни на один
  внешний домен (550 Relay denied) — автоматический тест на каждый билд smtp-сервиса.
- **Изоляция данных**: пользователь A не читает письмо/комнату пользователя B ни
  прямым API, ни поиском (фильтр ES), ни IMAP под своим логином.
- **Fail-open/closed контракты**: убить spamd — письма доставляются с пометкой;
  убить clamd — вложения блокируются, письма доставляются; убить ES — доставка
  идёт, поиск догоняет после восстановления (chaos-тесты на стенде перед релизом).
- **EICAR**: тестовый вирусный файл блокируется и в почте, и в чате.

## 10.3. Нагрузочные цели (ТЗ §11.2)

| Сценарий | Профиль | Порог прохождения |
|---|---|---|
| Веб API | 1000 виртуальных пользователей, микс почты/чата | p95 < 500 мс, ошибок < 0,1% за 30 мин |
| Чат | 1000 WS-соединений, 500 сообщений/мин | доставка p95 < 300 мс, ни одного потерянного |
| SMTP входящий | 5 писем/сек × 15 мин (100–500 КБ с вложениями) | очередь конвейера не растёт монотонно, 0 потерь |
| IMAP | 300 одновременных сессий IDLE + FETCH тяжёлых папок (50 тыс. писем) | SELECT < 2 с, список страницы < 200 мс из метаданных |
| Поиск | индекс 1 млн писем, 50 запросов/сек | p95 < 1 с (требование ТЗ §11.1) |

| Среда | Как проверяем |

## 10.5. Операционные тесты

- **Восстановление из бэкапа**: ежеквартально на стенде: чистый сервер → backup.ps1
  restore → контрольные ящики/чаты на месте, время фиксируется (цель ≤4 часов);
- **Откат релиза**: подъём предыдущей версии образов на актуальной схеме БД;
- **Алертинг**: `docker compose stop <сервис>` → email администратору ≤3 минут,
  повторное уведомление при длительном простое (escalation 30 мин для critical);
- **Ротация сертификатов и ключа JWT**: репетиция смены без разлогинивания всех
  пользователей (JWKS публикует оба ключа на время перехода).
