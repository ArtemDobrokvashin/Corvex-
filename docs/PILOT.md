# Пилот: 3–5 человек, одна неделя

Цель пилота — не «посмотреть, как выглядит», а получить три числа, по которым можно
решать о следующем шаге. Пока этих чисел нет, любое «готово к внедрению» — мнение.

## 1. Кого берём

- **3–5 человек**, которые каждый день пишут и получают почту по работе.
- Разные роли: минимум один руководитель (много переписки и вложений) и один сотрудник,
  который в основном получает письма.
- Один участник — с **внешним ящиком** (Mail.ru, Яндекс, Gmail), чтобы проверить миграцию.
- У всех должен быть доступ к старому ящику: пилот идёт параллельно, почта не теряется.

Пилот не заменяет рабочую почту. Все входящие продолжают приходить на старый адрес;
Corvex используется как второй клиент и как получатель перенесённого архива.

## 2. Что делаем в первый день

1. Создать учётные записи, выдать временные пароли.
2. Каждому — по одному контрольному письму с вложением (PDF и картинка), чтобы проверить
   отображение на его машине и браузере.
3. Подключить внешний ящик и запустить перенос архива.
4. Показать три действия: ответить, переслать с вложением, найти письмо поиском.
   Больше не показывать: пилот проверяет продукт, а не инструкцию.

## 3. Три метрики

### M1. Доставка входящих

Сколько писем, отправленных на адрес Corvex, действительно дошли и когда.

```sql
-- mail_db: дошли ли письма за период, по папкам
select f.name, count(*) as messages,
       min(m.internal_date) as first_seen,
       max(m.internal_date) as last_seen
from message_metadata m
join mail_folders f on f.id = m.folder_id
where m.internal_date > now() - interval '7 days'
group by f.name
order by messages desc;
```

Отдельно фиксируется **задержка**: разница между временем отправки (поле `Date` письма)
и `internal_date`. Ориентир: до 60 секунд для внутренних писем.

### M2. Успех переноса

```sql
-- mail_db: задания переноса и их исход
select status, mode, count(*) as jobs,
       sum(estimated_messages) as estimated,
       round(avg(extract(epoch from (finished_at - started_at)))) as avg_seconds
from mail_migration_jobs
where created_at > now() - interval '7 days'
group by status, mode;
```

Считается доля заданий в статусе `COMPLETED` и число писем, не перенесённых из-за ошибок.
Ориентир: ≥ 99 % писем перенесено, дублей нет (проверяется по `message_id_header`).

### M3. Обращения в поддержку

Отдельной системы обращений нет, поэтому ведётся вручную — таблица ниже заполняется в
конце каждого дня. Это честнее, чем подразумевать «метрику», которой не существует.

| День | Человек | Что случилось | Категория | Решено за |
|---|---|---|---|---|
| | | | вход / почта / вложения / скорость / непонятно | |

Категории нужны, чтобы отделить дефекты от непонимания интерфейса. Первые правятся в
коде, вторые — в подсказках.

## 4. Критерии исхода

| Итог | Условие |
|---|---|
| **Продолжаем** | M1: 100 % внутренних писем доставлено, задержка < 60 с; M2: ≥ 99 % перенесено, дублей 0; M3: ≤ 1 обращения на человека в неделю, все категории «непонятно» |
| **Продолжаем после исправлений** | дефекты есть, но каждый воспроизводим и локализован |
| **Стоп** | потеря письма, недоставка без объяснения, зависание переноса без восстановления |

Любая потеря письма останавливает пилот в тот же день: разбирается причина, пишется
строка в `STATUS.md`, и только потом пилот возобновляется.

## 5. Что пилот **не** проверяет

- приём почты из интернета (нет MX и порта 25);
- нагрузку 50 ящиков;
- работу дольше недели и поведение при перезапуске сервера;
- Chrome 109 и мобильные экраны, если таких участников не окажется;
- восстановление из бэкапа — это отдельная приёмка P3 в `ACCEPTANCE.md`.

Результаты пилота идут в `STATUS.md` отдельной строкой с датой и числами M1–M3.
