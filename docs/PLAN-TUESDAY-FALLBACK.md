# Запасной вариант вторника: сервер без домена

Если завтра вместо Thunderbird появится сервер — что делаем и что **не** обещаем.
Это не замена [`PLAN-TUESDAY.md`](PLAN-TUESDAY.md), а второй сценарий того же дня:
приёмка почтовых клиентов просто сдвигается на среду и никуда не исчезает.

Причина, по которой этот документ вообще нужен: почти вся работа на сервере делается
**без домена**, но три вещи без него не проверяются вовсе — внешняя почта, TLS с публичным
именем и PTR. Если начать с установки, а домен появится через неделю, окажется, что «сервер
готов» — это мнение, а не факт.

---

## 0. Что решаем до первой команды (10 минут)

Ответы на три вопроса определяют, будет ли день потрачен не зря. Секреты в чат не
присылаются — только «да/нет» и IP.

| Вопрос | Если «нет» | Если «да» |
|---|---|---|
| Есть SSH на сервер? | работать не с чем: день уходит на доступы | продолжаем |
| 16 ГБ RAM и 100 ГБ свободного диска на данных? | установка формально пройдёт, но ClamAV и Elasticsearch будут падать по памяти | продолжаем |
| Порты 25/443/587 не заняты IIS, Exchange или чужим nginx? | сначала освобождать; на занятом 25 почта не поднимется | продолжаем |

## 1. Порядок: сначала проверка, потом копирование (15 минут)

`preflight-server.ps1` уже есть в репозитории, но он рассчитан на хост с Docker и
запускается **на самом сервере**. Пока репозитория на сервере нет, проверять нечего — и
здесь появляется новая утилита, которую я добавил вместе с этим планом:

```powershell
python scripts\server_readiness.py --host <IP-сервера> --ssh-user <пользователь>
```

Что она делает, не меняя ничего на сервере:

- `ssh` с `BatchMode=yes` — никаких запросов пароля в скрипте; ключ или агент нужен заранее;
- `nproc`, память из `/proc/meminfo`, свободное место по `/`, время сервера;
- пороги из [`SERVER-REQUIREMENTS.md`](SERVER-REQUIREMENTS.md): 4 vCPU, 16 ГиБ RAM, 100 ГиБ;
- расхождение часов: больше 60 с — `FAIL`, потому что TLS, JWT и DKIM ломаются молча;
- занятость 80/443/25/587/993/995 — только если передан `--public-ip`, то есть проверка
  идёт **снаружи**, а не с самого сервера;
- 5432/6379/5672/9200 — должны быть закрыты снаружи; открытый порт базы — `FAIL`.

Отчёт пишется в `artifacts\smoke\server-readiness-<время>.json` вместе с SHA репозитория.
Коды возврата: `0` — блокеров нет, `1` — есть `FAIL`, `2` — `--strict` при наличии `WARN`.

**Чего этот прогон не доказывает:** ни домена, ни MX, ни SPF/DKIM/DMARC, ни PTR, ни TLS с
публичным именем, ни того, что Docker поставится и сборка пройдёт. Скрипт говорит это сам
последней строкой вывода, чтобы зелёный результат не приняли за «сервер готов».

## 2. Установка без домена (около часа, сборка 10–30 минут)

Всё по [`INSTALL.md`](INSTALL.md), с тремя поправками для режима без домена:

1. **Хост.** Linux-сервер — вариант C (Ubuntu 24.04 + Docker), а не Hyper-V: на выделенной
   машине виртуализация только добавляет слой. Windows Server — вариант A.
2. **Инициализация.** `./scripts/first-run.sh` без `--domain`: создаст `.env`, ключи JWT и
   DKIM, самоподписанный сертификат на 90 дней. Домены впишем позже — повторный запуск
   безопасен и не перезаписывает существующее.
3. **Почта выключена.** `.env.example` уже содержит `CORVEX_SMTP_ENABLED=false`,
   `CORVEX_IMAP_ENABLED=false`, `CORVEX_POP3_ENABLED=false`. Так и оставляем: без домена,
   MX и PTR почтовый контур не проверяется, а включённый и не проверенный контур — худший
   из вариантов.

Затем — предполётная проверка **там, где есть Docker**, и запуск:

```bash
python3 scripts/preflight.py
docker compose up -d --build
docker compose ps
```

Зачёт дня: 20 контейнеров в `healthy`, вход в веб-интерфейс по IP работает.

### Одна честная проблема, которую нельзя обойти молча

`preflight.py` внутри Linux-сервера и `scripts/*.ps1` на Windows-хосте — это две разные
машины. Копирование (`backup.ps1`, `restore.ps1`, `restore_verify.ps1`) написано на
PowerShell, и на чистом Ubuntu его нет. Приёмка P3 закрыта **для Windows-хоста**; на Linux
она закрытой не считается, пока не появится bash-версия или PowerShell 7 в сервере.

Варианты на завтра, в порядке предпочтения:

| Вариант | Что даёт | Цена |
|---|---|---|
| Сервер на Windows Server + Linux-VM | все скрипты работают как есть, P3 закрыт | слой Hyper-V, меньше памяти под сервисы |
| Ubuntu + PowerShell 7 (`apt install powershell`) | те же скрипты, но прогон будет первым | непроверенный сценарий, копия может упасть на путях |
| Ubuntu без копирования | установка и веб-проверки | **бэкапа нет** — на боевом железе это недопустимо |

Рекомендация: если сервер будет боевым, а не тестовым, — Windows Server с Linux-VM **или**
сразу bash-версия скриптов. Второе — моя работа на день, не ваша.

## 3. Что можно проверить без домена (и что нельзя)

| Проверяется | Чем | Зачёт |
|---|---|---|
| Вход администратором | браузер по IP | экран входа, смена временного пароля |
| Админка, права, квоты | браузер | пользователь создаётся, права применяются |
| Чат двух пользователей | два браузера | доставка в реальном времени, reconnect |
| Диск и ссылки | браузер + инкогнито | ссылка открывается без входа и отзывается |
| Календарь и напоминание | браузер | событие переживает перезапуск сервиса |
| Внутренняя почта (`company.local`) | браузер | письмо себе доходит, `av_status = CLEAN` |
| IMAP по IP | `login_probe.py --imap --host <IP>` | `IMAP LOGIN: SUCCESS` |
| Печать письма и файла | браузер | шапка и тело без интерфейса (P6) |

Нельзя, и это записывается как ограничение ресурса, а не как забытая галочка:

- письмо наружу и приём извне — нужны домен, MX, PTR и открытый 25;
- DKIM/SPF/DMARC у получателя — проверять нечем;
- TLS с публичным именем — сертификат на IP не выдаётся: Let's Encrypt не подписывает IP
  через обычный ACME, а самоподписанный даёт предупреждение в браузере;
- почтовые клиенты против настоящего домена — Thunderbird по IP можно, но это проверка
  протокола, а не боевой конфигурации.

## 4. Домен появился — что делаем дальше (около полутора часов)

Порядок жёсткий, потому что каждый шаг опирается на предыдущий:

1. `A`-запись `mail.<домен>` → IP; проверить распространение (`nslookup`).
2. Перезапустить `first-run.sh` с `--domain mail.<домен> --mail-domain <домен>` — он
   допишет отсутствующие переменные и не тронет ключи.
3. Сертификат Let's Encrypt: порт 80 открыт, `nginx` перезапускается с новым именем.
4. `MX`, SPF, DKIM (готовая TXT-строка из `first-run`), DMARC, PTR — у провайдера.
5. Только теперь `CORVEX_SMTP_ENABLED=true`, иначе почта принимается раньше, чем её есть
   чем защитить.
6. `mail-tester` — не ниже 9/10; письмо наружу и ответ снаружи в `INBOX`.
7. Включение IMAP/POP3 — это уже приёмка клиентов из [`PLAN-TUESDAY.md`](PLAN-TUESDAY.md),
   с PKCS12 для 993/995 ([`TESTING.md`](TESTING.md) §9).

Пункты 1–4 без вашего участия не делаются: нужна зона DNS и заявка на PTR.

## 5. Часы наблюдения: когда они действительно начнутся

72 часа считаются **не** с установки, а с момента, когда сервер работает на боевом домене
и получает настоящую почту. Правило прежнее и записано в [`ACCEPTANCE.md`](ACCEPTANCE.md):
отсчёт с дыркой (перезапуск, пересборка, падение хоста) — не отсчёт, он начинается заново.
На тестовом сервере без домена наблюдение не начинается: снимается только baseline, как на
ноутбуке 23.11.

---

## 6. Чего завтра не делаем

- Не направляем production MX на непроверенный сервер.
- Не включаем SMTP/IMAP/POP3 «чтобы проверить» до домена и PTR: включённый контур без
  DMARC и PTR портит репутацию IP быстрее, чем мы успеем её измерить.
- Не переносим рабочие ящики.
- Не строим G4 (Spring BOM, Alloy) в тот же день: унификация major-уровня требует повтора
  G1–G3, а приёмка клиентов ещё не закрыта.
- Не начинаем 72 часа на тестовом сервере.

## 7. Если сервер не появится

Тогда день идёт по [`PLAN-TUESDAY.md`](PLAN-TUESDAY.md): IMAP в Thunderbird, POP3,
документация. Ничего из этого документа не пропадает — он остаётся на случай, когда сервер
появится в среду, четверг или позже.

## 8. Что нужно от вас, чтобы этот план сработал

1. Ответы на три вопроса из §0 (IP, память, заняты ли 25/443).
2. SSH-доступ **по ключу** — пароль в чат не нужен и не принимается; если только пароль,
   скажите, и мы пойдём через интерактивный вход в вашем терминале.
3. Решение по бэкапу (§2): Windows Server, PowerShell 7 на Ubuntu или «пока без копий».

Первый шаг — одна команда, её вывод жду:

```powershell
python scripts\server_readiness.py --host <IP-сервера> --ssh-user <пользователь>
```
