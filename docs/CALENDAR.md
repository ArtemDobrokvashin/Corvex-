# Календарь Corvex — серверные события и напоминания

Документ фиксирует, что реально работает после подключения календаря к backend, чем это
проверено и какие ограничения остаются. Дата: 2026-10-19.

## Что изменилось

До этой итерации календарь существовал только в браузере: события лежали в
`localStorage`, напоминания срабатывали, пока открыта вкладка, а на сервере не было ни
таблиц, ни API. Теперь события хранятся в PostgreSQL, синхронизируются между сессиями и
устройствами одного пользователя, а напоминания отправляет сервер — браузер может быть
закрыт.

Серверная часть живёт в **`mail-storage-service`**, а не в новом сервисе: это уже
единственный сервис с PostgreSQL, Flyway, JPA и проверкой JWT по JWKS, поэтому
календарь не потребовал ни нового контейнера, ни новой схемы развёртывания, ни
изменения Compose. Отправка писем остаётся в `notification-service`, который уже владеет
SMTP-каналом служебных сообщений.

```
браузер ──JWT──> web-gateway ──> mail-storage-service  /api/v1/calendar/events
                                        │
                                        ├─ PostgreSQL: calendar_events, calendar_reminder_deliveries
                                        └─X-Corvex-Internal-Token──> notification-service
                                                                     /internal/calendar/reminders → SMTP
```

## Модель данных

`calendar_events`:

| Поле | Смысл |
| --- | --- |
| `starts_at`, `ends_at` | момент времени в UTC (`timestamptz`), `ends_at > starts_at` |
| `time_zone` | IANA-зона события, например `Europe/Amsterdam` |
| `all_day` | событие на весь день |
| `recurrence` | `none`, `daily`, `weekdays`, `weekly`, `monthly` |
| `reminder_minutes` | 0…10080 минут до начала; `NULL` — без напоминания |
| `priority`, `busy_status` | `high/medium/low`, `busy/tentative/free` |
| `attendees` | до 50 участников, по одному в строке |
| `source_kind`, `source_mail_id`, … | связь с письмом: `MAIL` требует существующего письма **этого же** владельца |
| `revision` | защита от перезаписи чужой правки |
| `deleted_at` | мягкое удаление |

Почему хранятся и момент, и зона: `Europe/Amsterdam` переключается на летнее время.
Если хранить только UTC-смещение или пересчитывать «каждые 24 часа», событие «в 09:00»
после перехода показывалось бы в 10:00. Вхождения повторений строятся из локальной даты и
локального времени в зоне события (`CalendarRecurrence`).

## API

Все методы требуют JWT; владелец всегда берётся из `sub` токена, идентификатор события
сам по себе доступа не даёт.

| Метод | Путь | Право | Смысл |
| --- | --- | --- | --- |
| `GET` | `/api/v1/calendar/events?from=&to=` | `CALENDAR_READ` | события в диапазоне (пересечения по времени + повторяющиеся) |
| `GET` | `/api/v1/calendar/events/{id}` | `CALENDAR_READ` | одно событие |
| `POST` | `/api/v1/calendar/events` | `CALENDAR_WRITE` | создать |
| `PUT` | `/api/v1/calendar/events/{id}` | `CALENDAR_WRITE` | изменить; обязательна `revision` |
| `DELETE` | `/api/v1/calendar/events/{id}?revision=` | `CALENDAR_WRITE` | мягко удалить |

Коды ошибок содержательные: `400` — что именно неверно (конец раньше начала, неизвестная
зона, больше 50 участников, напоминание вне 0…10080), `404` — события или письма-источника
нет у этого пользователя, `409` — `revision` устарела (событие изменили в другом окне),
`403` — нет права.

Права `CALENDAR_READ` / `CALENDAR_WRITE` добавлены в `Permission.java` и выданы всем
стандартным группам миграцией `V6__calendar_permissions.sql` (`SUPER_ADMIN` получает все
права из кода).

## Напоминания

1. Планировщик `CalendarReminderScheduler` раз в минуту смотрит события с напоминанием в
   окне «сейчас − 2 часа … сейчас + 8 дней».
2. Для каждого наступившего вхождения создаётся строка `calendar_reminder_deliveries`
   (`PENDING`) с уникальным ключом `(event_id, occurrence_at)`.
3. Строки забираются под `PESSIMISTIC_WRITE` и переводятся в `SENDING` **до** отправки.
   Второй экземпляр сервиса не увидит их и не отправит дубль.
4. `notification-service` формирует письмо и отправляет его через SMTP. Не-2xx ответ
   считается сбоем: строка возвращается в `PENDING` с задержкой 1/2/4/8 минут, после
   5 попыток — `FAILED`.
5. Если процесс упал между отправкой и отметкой `SENT`, строка останется в `SENDING`;
   через 10 минут она вернётся в очередь. Гарантия — **at-least-once**: в этом узком
   случае возможен повтор, но не потеря.
6. Удаление события отменяет его незавершённые напоминания.

Напоминание не отправляется, если встреча началась больше двух часов назад: после
долгого простоя сервера старые напоминания — шум, а не польза.

## Frontend

- `src/api/calendarApi.ts` — контракт, конвертация «дата + HH:MM ↔ instant» через
  `Intl.DateTimeFormat` и зону события (два прохода, чтобы не ошибиться у границы перехода
  на летнее время), маппинг в `CalendarEventItem`.
- `src/store/calendarStore.ts` — `setOwner(userId, demoMode, serverMode)`. В серверном
  режиме список сразу показывается из кэша `localStorage`, затем заменяется ответом
  сервера; локальные события без серверного id сохраняются, чтобы работа без сети не
  теряла данные.
- Создание/изменение/удаление обновляют интерфейс немедленно и уходят на сервер в фоне.
  `409` показывается как «Событие изменено в другом окне. Обновите календарь.», недоступный
  сервер — как «Событие сохранено только в этом браузере…». Молча ничего не теряется.
- Демо-режим остаётся локальным: показ интерфейса не требует backend.
- В боковой панели календаря видна подпись про серверные напоминания, а в карточке
  события — что напоминание придёт на почту и при закрытом браузере.

## Развёртывание

Никаких новых контейнеров. В `docker-compose.yml` у `mail-storage-service` появились
`CORVEX_NOTIFICATION_SERVICE_URL` и `CORVEX_CALENDAR_FROM`; у `notification-service` —
`CORVEX_CALENDAR_FROM`. Токен `CORVEX_INTERNAL_API_TOKEN` уже требовался обоим сервисам.

После обновления:

```bash
docker compose up -d --build mail-storage-service notification-service web-gateway frontend
docker compose logs --tail=100 mail-storage-service notification-service
```

Ожидаемо в логах: успешная миграция `V8__calendar.sql`, отсутствие ошибок Flyway, старт
`mail-storage-service` без `BeanCreationException`.

## Проверка на ПК

1. Войти пользователем с правом `CALENDAR_WRITE`, открыть «Календарь», создать событие
   через 10 минут с напоминанием «за 5 минут».
2. Обновить страницу (F5) и открыть календарь в другом браузере/профиле — событие на месте.
3. Закрыть браузер и дождаться времени напоминания: письмо от `corvex-calendar@…` должно
   прийти на почту пользователя.
4. Изменить событие во второй сессии, затем сохранить устаревшую версию в первой —
   ожидается сообщение о конфликте, а не перезапись.
5. Удалить событие и убедиться, что после обновления страницы оно не вернулось, а
   напоминание не пришло.
6. Перезапустить `mail-storage-service` между созданием напоминания и его отправкой —
   напоминание должно уйти после старта (в пределах 2 часов от начала встречи).

Быстрая проверка API без UI:

```bash
curl -s -H "Authorization: Bearer $ACCESS" \
  "https://localhost/api/v1/calendar/events?from=2026-10-01T00:00:00Z&to=2026-11-01T00:00:00Z"
```

## Ограничения текущего этапа

- Напоминания приходят только по почте; push/desktop-уведомления и мессенджеры не
  подключены.
- Текст письма-напоминания на русском: у `auth-service` нет локали пользователя в
  профиле, которую можно передать в `notification-service`.
- Повторение не поддерживает «последний день месяца», исключения отдельных вхождений и
  редактирование «только это вхождение» — меняется вся серия.
- Общие календари, приглашения участникам с ответом «принято/отклонено» и проверка
  занятости коллег не реализованы: `attendees` — список для отображения.
- Импорт ICS не реализован (экспорт был и остаётся на клиенте).
- Напоминания одного события идут владельцу; участники письмо не получают.
- Связь с чатом в схеме предусмотрена (`source_kind = 'CHAT'`), но UI-поток «создать
  событие из сообщения» ещё не сделан и не заявлен в интерфейсе.
- Адресная книга с импортом сотрудников, поиск по адресам отправленных писем и
  drag-and-drop событий в сетке — следующий этап, в этой итерации их нет.

## Что проверено автоматически

- `frontend`: `tsc -b` без ошибок; 66 файлов / 308 тестов, включая конвертацию времени
  через летнее время, синхронизацию с сервером, конфликт `409` и работу без сети.
- `mail-storage-service`: `CalendarRecurrenceTest` (летнее время, будни, недельное,
  месячное на 31-е), `CalendarServiceRulesTest` (участники, лимиты, backoff).
- `CalendarSchemaPostgresIT` проверяет ограничения схемы на настоящем PostgreSQL
  (Testcontainers). Имена `*IT` не входят в стандартный набор surefire, поэтому на ПК:

```bash
mvn -pl services/mail-storage-service -Dtest=CalendarSchemaPostgresIT test
```

Ожидаемо: 4 теста PASS при запущенном Docker.
- Java-компиляция в sandbox недоступна (нет JDK/Maven) — прогон `mvn test` выполняется на
  ПК пользователя.

## Дополнительные тесты сервиса уведомлений

`CalendarReminderControllerTest` проверяет без поднятия Spring-контекста: время в зоне
события (07:00Z → 09:00 Europe/Amsterdam), отказ без токена и при пустом токене
(fail-closed), отказ на некорректный адрес до обращения к SMTP, `503` при ошибке SMTP
(чтобы планировщик повторил доставку) и честный текст «Событие уже началось» для
просроченного напоминания.

