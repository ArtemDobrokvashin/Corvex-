# Определение готовности и приёмка

Документ отвечает на два вопроса: **когда задача считается сделанной** и **чем это
доказывается**. Он существует потому, что «сделано» обсуждалось в переписке и терялось
при смене сессии, а `STATUS.md` фиксировал результат постфактум, без правила.

## 1. Правило «готово»

Задача считается выполненной, когда выполнены **все четыре** условия. Частичное
выполнение означает «в работе», а не «сделано».

| № | Условие | Что значит на практике |
|---|---|---|
| 1 | **Живая проверка** | сценарий пройден на запущенном стенде человеком, а не только тестом |
| 2 | **Тест** | поведение закреплено автоматически; падение теста означает регресс |
| 3 | **Документация** | в `docs/` описано то, что действительно работает, включая ограничения |
| 4 | **Строка-доказательство** | в `STATUS.md` есть строка: команда, коммит, вывод и колонка «чего это не доказывает» |

Формулировка доказательства обязательна и должна содержать три элемента: **что
запускали**, **на каком коммите**, **что получили**. Фраза «сборка зелёная» без модуля
и SHA доказательством не является — именно так блокер `DkimKeyRingTest` прожил в `main`.

Запрещено писать в документации о функции, которой нет в коде. Обратное направление
тоже верно: если функция есть, но не описана в `STATUS.md`, она считается незавершённой.

## 2. Стоп-лист

До закрытия четырёх приёмок из §3 **не начинаются**:

- этап 5 переноса почты (MBOX/EML);
- новые функции календаря, чата и диска;
- переезд почтового ядра на James;
- любые работы, требующие нового сервера или домена.

Разрешены только: исправления найденных при приёмке дефектов, документация и CI.

Исключение оформляется явно: одна строка в этом файле с датой и причиной. Иначе
стоп-лист перестаёт действовать после первого же «ну это же быстро».

## 3. Четыре приёмки

Это не «ещё немного поправить», а четыре независимых доказательства, что систему можно
ставить людям.

### P1. Живой вход через Google

**Зачем:** без OAuth внешние ящики Gmail/Workspace остаются непроверенным обещанием, а
Microsoft 365 иначе не подключается вовсе.

**Как:** стенд поднят, `CORVEX_PUBLIC_BASE_URL` указывает на тот же origin, что
зарегистрирован у провайдера.

```powershell
docker compose --profile local-oauth up -d
# приложение Google: Web client, redirect URI = <base>/api/v1/mail/external-accounts/oauth/callback
```

Сценарий: вход в Corvex → «Почта» → подключить внешний ящик → Google → согласие →
возврат на `/mail?oauth=connected…` → в списке появился ящик → сбор писем → отзыв
согласия в консоли Google → следующая попытка сбора даёт `reauthRequired` и `409` →
повторный вход восстанавливает сбор.

**Доказательство:** строка в `STATUS.md` с датой, провайдером, числом собранных писем,
кодом ответа после отзыва согласия.

**Чего не доказывает:** работу с Microsoft 365 (отдельный провайдер), поведение на
архиве в тысячи писем, устойчивость при недельной работе (Google в статусе Testing
выдаёт refresh-токен на 7 дней).

### P2. Полный `mvn verify` по всему reactor

**Зачем:** до сих пор ни один полный прогон на текущем `main` не был зелёным; проверялся
только модуль `mail-storage-service`.

**Как:**

```powershell
mvn -B -ntp clean verify
```

**Доказательство:** `BUILD SUCCESS`, суммарное `Tests run:` по всем модулям и SHA коммита.
Артефакт CI-прогона прикладывается ссылкой.

**Чего не доказывает:** поведение под нагрузкой, работу с реальными PostgreSQL/RabbitMQ
(тесты используют заглушки), Docker-образы.

### P3. Восстановление из бэкапа на чистых томах

**Зачем:** копия без проверенного восстановления — не бэкап, а надежда. Сейчас ни один
прогон восстановления не зафиксирован.

**Как** (порядок важен: сначала копия, потом изолированный restore, потом сверка):

```powershell
powershell -ExecutionPolicy Bypass -File scripts\backup.ps1 -BackupRoot D:\CorvexBackup
powershell -ExecutionPolicy Bypass -File scripts\restore.ps1 `
  -BackupDir D:\CorvexBackup\<timestamp> -ProjectName corvex-restore-drill -DataOnly -Force
powershell -ExecutionPolicy Bypass -File scripts\restore_verify.ps1 `
  -BackupDir D:\CorvexBackup\<timestamp> -ProjectName corvex-restore-drill
```

`restore.ps1` и `restore_verify.ps1` требуют `-BackupDir` — без него скрипт падает на
обязательном параметре. В `docs/OPERATIONS.md` этот параметр раньше был пропущен; исправлено.

**Доказательство:** вывод `restore_verify.ps1` (четыре базы и три тома совпали) и
контрольный ящик: письмо, вложение, событие календаря, комната чата — открываются после
восстановления.

**Чего не доказывает:** восстановление на другой машине, поведение при обрыве посреди
restore, время восстановления на объёме больше текущего.

### P4. Установка с нуля

**Зачем:** сейчас все проверки шли на существующих томах. Чистая установка — первый опыт
клиента.

**Как** (на машине, где данные не нужны):

```powershell
git clone https://github.com/ArtemDobrokvashin/Corvex-.git corvex-clean
cd corvex-clean
Copy-Item .env.example .env      # заполнить пароли и ключи
docker compose up -d --build
docker compose ps                # все сервисы healthy
```

**Доказательство:** перечень контейнеров со статусом `healthy`, применённые миграции
`V1…V13`, вход первым администратором, отправка и получение письма внутри домена.

**Чего не доказывает:** приём почты из интернета (нужен MX и порт 25), работу под
нагрузкой 50 ящиков, 72 часа без перезапуска.

Правило обновления: строка меняется только вместе с доказательством. Перенос из «в работе»
в «пройдено» без вывода команды запрещён.

## 5. Аудит документации против кода (одноразовый, до пилота)

Проверка автоматизирована в `scripts/docs_audit.py`, чтобы её не пришлось повторять глазами;
`scripts/tests/test_docs_audit.py` не даёт результату испортиться. Сверяются пять вещей:
маршруты OpenAPI с настоящими `@*Mapping`, живые маршруты с документацией, ссылки на файлы,
номера миграций и переменные `.env`.

| Что было не так | Как исправлено |
|---|---|
| `PATCH /mail/folders/{folderId}` обещал переименование папки, которого нет ни в контроллере, ни в интерфейсе | помечено `x-corvex-status: planned`; `MAIL.md`, `USER-GUIDE.md`, `API.md` больше не утверждают, что переименование работает; задача добавлена в `ROADMAP.md` |
| `DELETE /mail/messages/{messageId}` обещал удаление, которого нет: «удалить» = перемещение в `TRASH` | помечено `planned`, в описании сказано, что жёсткое удаление есть только во внутреннем контуре |
| `auth-api.yaml` показывал JWKS как публичный путь gateway | путь оставлен, но с `x-corvex-status: internal`, собственным `servers` (`auth-service:8081`) и объяснением, что снаружи он недостижим |
| Черновики (кроме создания), предпросмотр вложений и Office-превью чата работали, но не были описаны | добавлены 6 операций и 3 схемы в `mail-api.yaml`, 1 операция в `chat-api.yaml` |
| Эндпоинты James-провижининга и чтения не были описаны нигде | раздел `3.2` в `API.md`: включаются флагами, по умолчанию отвечают `404` |
| `ROADMAP.md` и `STATUS.md` заявляли миграции до `V8`, фактически их 13 | исправлено; у каждого сервиса своя нумерация, `V1…V13` — это `mail-storage-service` |

Что осталось осознанно незакрытым: **84 переменные** читаются сервисами, но не описаны в
`.env.example` (проверка их не требует). Из них 57 имеют значения по умолчанию в
`application.yml` — это настроечные ручки (лимиты IMAP, кэш предпросмотра, тайм-ауты), 11 —
внутренняя проводка compose (адреса сервисов, пути к ключам James), остальные — переменные
тестовых скриптов и `@ConfigurationProperties` внешней почты. Ни одна из них не обязательна
к заполнению: compose не требует ни одной `CORVEX_*` без значения по умолчанию, и это теперь
тоже проверяется (`check_compose_requires_documented`).

Чего аудит **не** доказывает: что описания полей, коды ответов и тексты ошибок совпадают с
кодом. Он сверяет только существование маршрута, файла, миграции и переменной.
